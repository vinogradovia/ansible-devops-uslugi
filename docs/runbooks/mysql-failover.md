# Инструкция: переключение MySQL при аварии, обратное переключение, восстановление из копии

Для кого этот документ: разработчик/дежурный без глубоких знаний MySQL, у которого есть доступ к
Ansible-контроллеру (репозиторий + Ansible Vault пароль) и к VPN/сети, где живут серверы БД.
Архитектура и проектные решения, на которых основана эта инструкция, — см.
[`docs/adr/0004-mysql-ha-replication-role.md`](../adr/0004-mysql-ha-replication-role.md) (роли
`mysql_replication`, `proxysql`).

## Топология одним взглядом

- **primary** — основной сервер, принимает запись. Один хост, группа `mysql_primary`.
- **read-реплика** — тот же ДЦ, что и primary. Обслуживает читающий трафик сайта в обычном
  режиме. Группа `mysql_read_replica`.
- **DR-реплика** — другой ДЦ Selectel. В обычном режиме не обслуживает никакой боевой трафик,
  только принимает репликацию. Группа `mysql_dr_replica`.
- **ProxySQL** — отдельные хосты, единственная точка подключения для приложений (`db-write`,
  `db-read` через DNS). Сам решает, на какой сервер MySQL отправить запрос, по таблице
  backend-серверов (writer-hostgroup 10 / reader-hostgroup 20).

**Важно про DNS:** `db-write`/`db-read` всегда указывают на хосты ProxySQL и **не меняются** ни
при переключении, ни при обратном переключении — меняется только то, какой сервер MySQL ProxySQL
считает writer'ом/reader'ом. Ни один шаг ниже не трогает DNS.

## ⚠ Главное предостережение перед началом

Пока идёт авария или учебное переключение — **не запускайте обычный (без тегов/лимитов)
Ansible-прогон** на группы `mysql_primary` / `mysql_read_replica` / `mysql_dr_replica`. Роль
`mysql_replication` идемпотентна и при обычном прогоне попытается вернуть хосты в «штатное»
состояние по inventory (например, заново включит `read_only` на DR и попробует подключить её
репликацией обратно к исходному primary) — это оборвёт экстренное переключение. Используйте
только команды, указанные в шагах ниже (с явными `--tags`/`--limit`).

## Предварительные условия

- Доступ к Ansible-контроллеру с этим репозиторием и файлом пароля Ansible Vault
  (`group_vars/*/vault.yml`).
- SSH/VPN-доступ к хостам `mysql_primary`, `mysql_read_replica`, `mysql_dr_replica`, ProxySQL —
  тот же межДЦ-туннель, через который идёт репликация.
- Знать актуальные имена ваших плейбуков-оркестраторов (ниже используются условные имена
  `mysql-replicas.yml` и `proxysql.yml` — замените на реальные).

## Раздел 1. Как понять, что нужно переключение

Авария primary — это НЕ то же самое, что временная просадка сети. Прежде чем переключаться,
убедитесь:

1. Сайт действительно не может писать в базу (ошибки записи заказов/анкет, а не просто
   медленные ответы).
2. Primary недоступен не только с одного хоста, а по факту (попробуйте с ProxySQL-хоста):
   ```bash
   mysqladmin -h <ip_primary> -u root -p ping
   ```
   Если не отвечает или отвечает ошибкой соединения (не «Access denied» — это как раз означает,
   что сервер жив) — переходите к разделу 2.
3. **Если авария затронула весь ДЦ основного сервера** (не только сам сервер), read-реплика
   (тот же ДЦ) тоже, скорее всего, недоступна. Тогда временно потребуется направить на DR-реплику
   не только запись, но и чтение — это отмечено отдельным шагом ниже.

## Раздел 2. Экстренное переключение на DR-реплику

Ожидаемое время выполнения — несколько минут (соответствует требованию ТЗ «переключиться за
минуты»). Засеките время начала и окончания — это нужно для отчёта по итогам учений/инцидента.

### Шаг 1. Если старый primary технически доступен (но недоступен приложению) — защититься от split-brain

Если primary отвечает на подключение (проблема, например, только в сети до ProxySQL), сразу
запретите на нём запись, чтобы после восстановления сети он случайно не принял «чужую» запись:

```bash
mysql -h <ip_primary> -u root -p -e "SET GLOBAL super_read_only=ON; SET GLOBAL read_only=ON;"
```

Если primary полностью недоступен (сервер/ДЦ не отвечает вообще) — этот шаг просто невыполним,
пропустите его и идите дальше.

### Шаг 2. Проверить, что DR-реплика готова принять роль writer'а

Подключитесь к DR-реплике и посмотрите отставание:

```bash
mysql -h <ip_dr_replica> -u root -p -e "SHOW REPLICA STATUS\G" | grep -E "Seconds_Behind_Source|Replica_IO_Running|Replica_SQL_Running"
```

- `Seconds_Behind_Source` — сколько секунд DR отстаёт от primary. Чем меньше, тем меньше
  потенциальная потеря данных (записи за эти секунды, не успевшие реплицироваться, будут
  потеряны — это ожидаемое следствие асинхронной репликации, зафиксированное в ТЗ).
- Если `Replica_IO_Running`/`Replica_SQL_Running` не `Yes` — репликация уже была сломана до
  аварии. Прежде чем переключаться, оцените: DR может быть неактуальна. В большинстве случаев
  всё равно переключаемся (это лучше, чем полная недоступность сайта), но сообщите об этом в
  отчёте по инциденту отдельно.

### Шаг 3. Перевести DR-реплику в writable-режим

```bash
ansible-playbook -i inventory.yml mysql-replicas.yml \
    --tags mysql_replication_promote --limit <dr-replica-host>
```

Эта команда (задачи роли `mysql_replication`, `tasks/promote.yml`) на DR-реплике выполнит:
`STOP REPLICA` → `RESET REPLICA ALL` → снимет `read_only`/`super_read_only`. После этого DR
технически может принимать запись.

### Шаг 4. Переключить ProxySQL на новый writer

```bash
ansible-playbook -i inventory.yml proxysql.yml \
  -e "proxysql_backend_servers=[{'hostgroup': 10, 'address': '<ip_dr_replica>', 'port': 3306}]"
```

Это заменит содержимое writer-hostgroup (10) на DR-реплику (задачи `sync-backend-servers.yml`
роли `proxysql` полностью пересобирают строки в управляемых hostgroups). Если авария затронула
весь ДЦ и read-реплика тоже недоступна (см. раздел 1, пункт 3) — временно добавьте DR и в
reader-hostgroup (20) тем же способом, чтобы чтение тоже шло на неё:

```bash
ansible-playbook -i inventory.yml proxysql.yml \
  -e "proxysql_backend_servers=[{'hostgroup': 10, 'address': '<ip_dr_replica>', 'port': 3306}, {'hostgroup': 20, 'address': '<ip_dr_replica>', 'port': 3306}]"
```

### Шаг 5. Проверить, что сайт работает

- Открыть публичный фронт — страницы загружаются.
- Оформить **тестовый заказ** и убедиться, что он корректно сохранился (это же — приёмочный
  критерий ТЗ, пункт 5).
- Проверить в логах ProxySQL/приложения, что запросы реально идут на новый writer, а не падают.

### Шаг 6. Зафиксировать

- Время начала (недоступность primary) и время, когда сайт снова заработал на DR — это метрика
  для отчёта.
- Кратко записать причину аварии (если известна) и состояние read-реплики (была ли она тоже
  недоступна).

## Раздел 3. Обратное переключение (failback) — без потери данных

Выполняется **после** того, как исходный ДЦ/сервер primary полностью восстановлен и проверен.
Это не симметричная операция шагу 2 — чтобы не потерять данные, записанные во время аварии на
DR, старый primary сначала **временно становится репликой DR**, догоняет её, и только после
полной синхронизации происходит обратное переключение. Выполнять в согласованное окно (см. ТЗ,
раздел «Процесс»).

### Шаг 1. Убедиться, что старый primary снова здоров

MySQL запущен, сеть/VPN до него работает, диск не переполнен. Явно защитить его от случайной
записи:

```bash
mysql -h <ip_old_primary> -u root -p -e "SET GLOBAL super_read_only=ON; SET GLOBAL read_only=ON;"
```

### Шаг 2. Подключить старый primary репликой к новому writer'у (DR)

Пароль репликационного пользователя — тот же, что в Ansible Vault
(`mysql_replication_repl_password`):

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='<ip_dr_replica>',
  SOURCE_PORT=3306,
  SOURCE_USER='repl',
  SOURCE_PASSWORD='<пароль_из_vault>',
  SOURCE_AUTO_POSITION=1;
START REPLICA;
```

Это делается вручную (не через `ansible-playbook`), потому что задачи роли `mysql_replication`
рассчитаны на штатную топологию (primary статически не умеет быть репликой) — см. ADR §7.

### Шаг 3. Дождаться полной синхронизации

Периодически проверяйте на старом primary:

```bash
mysql -h <ip_old_primary> -u root -p -e "SHOW REPLICA STATUS\G" | grep -E "Seconds_Behind_Source|Replica_IO_Running|Replica_SQL_Running"
```

Ждите `Seconds_Behind_Source: 0` и оба `Running` в `Yes`. Дополнительно сверьте, что
GTID-множества совпадают на обоих хостах (должны быть идентичны при нулевом отставании):

```bash
mysql -h <ip_old_primary>  -u root -p -e "SELECT @@GLOBAL.gtid_executed;"
mysql -h <ip_dr_replica>   -u root -p -e "SELECT @@GLOBAL.gtid_executed;"
```

**Не переходите к шагу 4, пока значения не совпадут.** Именно это условие гарантирует
«обратное переключение без потери данных» (приёмочный критерий ТЗ, пункт 6).

### Шаг 4. Короткая пауза записи и собственно переключение

В согласованное окно, когда GTID-множества совпали:

1. Кратковременно остановить запись на текущем writer'е (DR):
   ```bash
   mysql -h <ip_dr_replica> -u root -p -e "SET GLOBAL super_read_only=ON; SET GLOBAL read_only=ON;"
   ```
2. Повторно проверить (шаг 3) — GTID должны совпасть окончательно (новых записей больше не
   было).
3. На старом primary — вернуть его в роль writer'а:
   ```sql
   STOP REPLICA;
   RESET REPLICA ALL;
   SET GLOBAL super_read_only=OFF;
   SET GLOBAL read_only=OFF;
   ```
   (те же три команды, что выполняет `tasks/promote.yml` для DR — здесь вручную, по той же
   причине, что и в шаге 2).
4. Переключить ProxySQL обратно:
   ```bash
   ansible-playbook -i inventory.yml proxysql.yml \
     -e "proxysql_backend_servers=[{'hostgroup': 10, 'address': '<ip_old_primary>', 'port': 3306}, {'hostgroup': 20, 'address': '<ip_read_replica>', 'port': 3306}]"
   ```

### Шаг 5. Вернуть DR-реплику в режим ожидания

DR должна снова стать обычной репликой исходного primary (её `mysql_replication_role` в
inventory и так `dr_replica` — она не поменялась). Это можно сделать штатным прогоном роли:

```bash
ansible-playbook -i inventory.yml mysql-replicas.yml --limit <dr-replica-host>
```

Роль увидит, что хост больше не реплика (`Is_Replica: false`), и заново подключит её к
`mysql_replication_primary_host` (исходному primary) через `CHANGE REPLICATION SOURCE`, включит
`read_only`/`super_read_only`. Если read-реплика тоже временно обслуживала чтение (см. раздел 2,
шаг 4) — она к этому моменту уже не в reader-hostgroup ProxySQL (шаг 4 этого раздела убрал DR из
обеих hostgroups), проверьте, что read-реплика сама всё ещё исправно реплицируется от primary
(обычно да — если она не была задействована в аварии, её ничего не трогало).

### Шаг 6. Проверить и зафиксировать

- Тестовый заказ снова проходит.
- Чтение идёт на read-реплику, запись — на primary (по логам ProxySQL, как и в разделе 2, шаг 5).
- Записать время окончания обратного переключения.

## Раздел 4. Восстановление из архивной копии на тестовый сервер

Бэкапы (`xtrabackup`/`mariabackup`) лежат в S3 (Selectel object storage), в префиксах
`daily/`, `weekly/`, `monthly/` — см. `roles/mysql_replication`, `tasks/backup.yml`. Каждый файл
уже прошёл `--prepare` перед загрузкой, поэтому дополнительная подготовка при восстановлении не
нужна — сразу `--copy-back`.

### Шаг 1. Посмотреть список доступных копий

Выполнить с хоста, где уже настроен `rclone` (обычно — DR-реплика, если бэкапы настроены по
умолчанию), либо настроить `rclone` на тестовом сервере с теми же S3-credentials из Vault:

```bash
rclone lsf mysql_backup_s3:<bucket>/daily
```

(замените `daily` на `weekly`/`monthly`, если нужна более старая копия).

### Шаг 2. Скачать нужный архив на тестовый сервер

```bash
rclone copy mysql_backup_s3:<bucket>/daily/<timestamp>.tar.gz /tmp/restore/
```

### Шаг 3. Установить `xtrabackup`/`mariabackup` на тестовом сервере

Тот же пакет и репозиторий, что использует роль `mysql_replication`
(`roles/mysql_replication/tasks/backup.yml`, репозиторий Percona) — версия должна соответствовать
версии MySQL, из которой снят бэкап.

### Шаг 4. Распаковать и восстановить

```bash
mkdir -p /tmp/restore/extracted
tar -C /tmp/restore/extracted -xzf /tmp/restore/<timestamp>.tar.gz

systemctl stop mysql
rm -rf /var/lib/mysql/*
xtrabackup --copy-back --target-dir=/tmp/restore/extracted --datadir=/var/lib/mysql
chown -R mysql:mysql /var/lib/mysql
systemctl start mysql
```

**Тестовый сервер не должен быть подключен к боевой репликации и не должен участвовать в
ProxySQL** — это изолированная проверка, а не ещё одна реплика.

### Шаг 5. Проверить целостность данных

Подключиться и проверить, что ключевые таблицы (заказы, каталог) на месте и выглядят разумно
(количество строк, последние записи по времени — не путать «восстановилось» с «пустая база
без ошибок»):

```bash
mysql -u root -p -e "SELECT COUNT(*) FROM <db>.<orders_table>; SELECT MAX(created_at) FROM <db>.<orders_table>;"
```

Это закрывает приёмочный критерий ТЗ, пункт 7.

## Раздел 5. Список оповещений

| Алерт | Что означает | Что делать |
|---|---|---|
| `MysqlDown` (уже есть) | primary или реплика недоступны >1 мин | Если это **primary** — начинайте раздел 2 |
| Отставание репликации > 300 сек (добавляется вместе с этой ролью) | read- или DR-реплика отстаёт от primary | Если это read-реплика — сайт продолжает работать (пишет и читает часть с primary), но проверьте нагрузку/сеть. Если DR — не паниковать (она и так не под боевым трафиком), но не затягивать: во время реальной аварии именно её отставание определит потерю данных |
| Репликация сломана (`Replica_IO_Running`/`Replica_SQL_Running` ≠ `Yes`, добавляется вместе с этой ролью) | реплика не защищает от аварии, пока не почините | Разобраться в причине (сеть, конфликт данных); при необходимости — пересоздать реплику из свежего бэкапа (раздел 4, но `--copy-back` на саму реплику, а не тестовый сервер) |
| Суточный бэкап не создался (добавляется вместе с этой ролью, метрика `mysql_backup_last_success_timestamp_seconds`) | `mysql-backup.service` упал или таймер не сработал | `systemctl status mysql-backup.service`, `journalctl -u mysql-backup.service`, запустить вручную: `systemctl start mysql-backup.service` |

**Известное ограничение (см. ADR §13, ROADMAP P0 №1):** доставка алертов (Alertmanager) в
коллекции сейчас не работает ни в docker-, ни в k3s-режиме `monitoring_server`. Правила алертов
из этой таблицы будут срабатывать в VMAlert, но **не дойдут** до дежурного, пока этот баг не
закрыт отдельно. До этого момента отставание/разрыв репликации и пропущенный бэкап нужно
проверять руками (команды из разделов 2–4 выше), не полагаясь на автоматическое оповещение.
