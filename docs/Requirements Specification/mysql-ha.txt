# ТЗ: резервирование и разгрузка базы данных MySQL

## Цель
Сейчас база данных сайта (заказы, анкеты, каталог) - на одном сервере.
Если он умирает, сайт встаёт, данные под угрозой. Плюс весь объём чтения
тоже ложится на этот единственный сервер.

Нужно решить две задачи:
1. ОТКАЗОУСТОЙЧИВОСТЬ: живая копия базы в другом ДЦ, возможность переключиться на неё за минуты, и архивные копии на случай порчи/удаления.
2. РАЗГРУЗКА ЧТЕНИЯ: вынести читающие запросы (SELECT) на отдельную копию, чтобы снизить нагрузку на основной сервер.

## Что НЕ нужно (не предлагать без согласования)
- Мультимастер-кластер (Galera, InnoDB Cluster) - избыточно и менее надёжно при связи между ДЦ.
- Автоматическое переключение между ДЦ - риск «двух баз с разными данными».

## Топология (три роли, НЕ путать)
- ОСНОВНОЙ (primary) - принимает запись и чтение. Текущий сервер.
- РЕПЛИКА ДЛЯ ЧТЕНИЯ (read-replica) - желательно в ТОМ ЖЕ ДЦ, что и
  основной (чтобы чтение было быстрым, по локальной сети). На неё
  приложение шлёт читающие запросы для разгрузки основного.
- РЕЗЕРВНАЯ КОПИЯ для аварии (DR-replica) - в ДРУГОМ ДЦ (можно другая
  локация selectel). В обычном режиме приложение её НЕ нагружает - она
  ждёт аварии основного. Грузить её боевым чтением нельзя: это мешает
  быстрому и безопасному переключению в момент аварии.

Обе реплики получают данные с основного по непрерывной асинхронной
репликации (на GTID, формат бинлога ROW) и в обычном режиме работают в режиме «только чтение» (read_only / super_read_only).

## Что требуется сделать

1. Сервер read-реплики (в том же ДЦ, что основной) и сервер DR-реплики
   (в другом ДЦ). Версия MySQL на ОБОИХ - ТОЧНО как на основном.

2. Непрерывная репликация основной → обе реплики. Трафик репликации
   между ДЦ (до DR-реплики) - шифрованный, не открытым текстом.

3. Единая точка подключения вместо прямых IP. Все приложения
   (api, публичный фронт, админка) подключаются к базе через
   управляемые точки (DNS-имена с коротким TTL и/или ProxySQL):
   - точка «запись/основной» - переключается на DR-реплику при аварии;
   - точка «чтение» - указывает на read-реплику.
   Прямые IP в конфигурации приложений не используются.

4. Переключение при аварии - РУЧНОЕ, по письменной пошаговой инструкции на русском, понятной разработчику без глубоких знаний MySQL.

5. Ежесуточные архивные копии базы, хранение от 14 дней, на ОТДЕЛЬНОМ хранилище (не на серверах базы). Репликация бэкапом НЕ считается - она копирует и ошибочное удаление данных на все серверы.

6. Оповещения: репликация (любой из реплик) сломалась или отстаёт сверх порога; основной сервер недоступен; суточный бэкап не создался.

## Приёмка (показать вживую, «настроено на бумаге» не считается)
1. Запись на основном появляется на ОБЕИХ репликах за секунды.
2. Обе реплики защищены от записи в обычном режиме.
3. Показать, что читающие запросы сайта реально идут на read-реплику,
   а пишущие - на основной (по логам/статистике подключений).
4. Показать, что оформление тестового заказа корректно работает сразу
   после записи (свежие данные читаются с основного, не теряются).
5. Учебное переключение при аварии: перевести сайт на DR-реплику,
   показать, что сайт работает (страницы + тестовый заказ). Засечь время.
6. Учебное обратное переключение без потери данных.
7. Учебное восстановление из архивной копии на тестовый сервер.
8. Обрыв репликации → пришло оповещение.

## Передать по итогу
Схему конфигурации (три роли и точки подключения); инструкции
переключения, обратного переключения и восстановления из копии
(на русском); список оповещений.

## Процесс
Работы на боевой базе - только в согласованное окно, с предварительной
полной копией. Изменения поэтапно, после каждого - проверка, что сайт
работает. Пароли и доступы - не открытым текстом в переписке.
