# ADR-0005: Роли `postgresql_replication` и `odyssey` (отказоустойчивость и пулинг соединений PostgreSQL)

- **Статус:** Принято
- **Дата:** 2026-07-12
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

Отдельного письменного ТЗ (по аналогии с `docs/Requirements Specification/mysql-ha.txt`) для этой
работы нет — требования сформированы в диалоге и зафиксированы этим ADR. Задача по сути зеркальна
ADR-0004 (MySQL), но для PostgreSQL: нужна отказоустойчивость (DR-реплика в другом ДЦ Selectel) и
разгрузка чтения (read-реплика в том же ДЦ), плюс полноценные бэкапы. Автоматический failover и
мультимастер — не рассматриваются.

В коллекции уже есть смежная инфраструктура, на которую эта работа опирается (те же прецеденты,
что использованы в ADR-0004):

- `docs/adr/0004-mysql-ha-replication-role.md` — почти прямой архитектурный аналог: разделение
  ролей по объекту ответственности, adopt/fresh install, инвентарная модель `primary`/`read_replica`/
  `dr_replica`, ручной promote за тегом `never`, бэкапы с DR-реплики, Ansible Vault для секретов,
  molecule на vagrant/libvirt. Ниже решения там, где они дословно повторяют ADR-0004, помечены
  ссылкой на соответствующий параграф, а не переобосновываются заново.
- `infra_dns` уже умеет TTL на уровне отдельной записи (`record.ttl` в `templates/zone.j2`,
  добавлено в ADR-0004 §6) — используется для `db-write`/`db-read` без доработок.
- `monitoring_agent`/`monitoring_server` — процедура добавления нового экспортёра уже описана в
  `AGENTS.md` и применена для `mysqld_exporter`; используется тот же чек-лист для
  `postgres_exporter`.
- Собственных ролей для PostgreSQL, пулера соединений или repmgr-кластера в коллекции пока нет.
- Проверено отдельно (важно для §6): у `yandex/odyssey` GitHub Releases не содержат вложений
  (проверено через `GitHub API` — assets пустые для всех тегов, включая `v1.5.1`), только
  исходники тега. Зато пакет `odyssey` реально присутствует в `apt.postgresql.org` (PGDG) —
  проверено скачиванием `Packages.gz` для `bookworm-pgdg`, найден пакет `odyssey 1.5.0-1.pgdg12+1`.

## Решения

### 1. Состав новых ролей

**Решение:** две новые роли, а не одна — тот же принцип разделения, что и в ADR-0004 §1:

- **`postgresql_replication`** — всё, что выполняется *на серверах PostgreSQL* (primary,
  read-реплика, DR-реплика): установка/adopt PostgreSQL, конфигурация репликации через `repmgr`,
  физические бэкапы `pgBackRest` и их выгрузка в S3, ручной promote.
- **`odyssey`** — [Yandex Odyssey](https://github.com/yandex/odyssey) на отдельных выделенных
  хостах, с собственным жизненным циклом, не привязанным к жизненному циклу серверов БД —
  прямой аналог `proxysql` из ADR-0004 §1 (та же логика: пулер меняется независимо от серверов
  БД, не имеет доступа к данным).

### 2. Установка vs adopt существующего PostgreSQL

**Решение:** те же два пути, что и в ADR-0004 §2:

- **Adopt** — если на хосте уже обнаружен работающий PostgreSQL (`ansible.builtin.service_facts` +
  проверка версии через `pg_lsclusters`/`postgres --version`), роль **не переустанавливает**
  сервер: только донастраивает то, что нужно для репликации (`wal_level=replica`,
  `max_wal_senders`, `max_replication_slots`, `archive_mode=on` + `archive_command` для
  `pgBackRest`, drop-in файл в `conf.d/`), заводит репликационного пользователя и пользователя
  `repmgr` (роль `superuser`, отдельная база `repmgr`). Рестарт службы после правки конфигурации —
  не автоматический, только `notify` с ручным подтверждением (тот же паттерн, что и в
  ADR-0004 §2, — рестарт боевого primary без согласованного окна недопустим).
- **Fresh install** — если PostgreSQL не обнаружен (ожидаемый случай для read-реплики и
  DR-реплики), роль ставит PostgreSQL из официального PGDG apt-репозитория
  (`apt.postgresql.org`), GPG через `signed-by`-keyring (тот же паттерн, что и в
  `roles/docker/tasks/install-repo.yml` — **не** `apt_key`).

**Версия — фактическая версия primary, не жёсткий дефолт:** переменная
`postgresql_replication_version` по умолчанию — `17`, но этот дефолт актуален только когда primary
**тоже** ставится fresh. Если primary — adopt (может оказаться на более старой версии, например
14), версия для read/DR-реплик **всегда берётся из фактически обнаруженной версии primary**, а не
из дефолта — физическая streaming-репликация (и `repmgr` поверх неё) работает только между
одинаковыми мажорными версиями PostgreSQL, рассинхронизация версий сломает репликацию молча на
этапе `pg_basebackup`. Механизм проброса — тот же, что и в ADR-0004 §2: play на группе
`postgresql_primary` отрабатывает (или как минимум собирает факты) **до** play на
`postgresql_read_replica`/`postgresql_dr_replica`, обнаруженная версия пробрасывается через
`hostvars[groups['postgresql_primary'][0]].postgresql_replication_discovered_version`. Это
обязательное требование к порядку плеев — зафиксировать в README роли.

**Поддержка ОС:** Debian/Ubuntu (apt) — совпадает со scope всей коллекции (ADR-0002 §4).

### 3. Инвентарная модель и параметр роли хоста

**Решение:** три группы инвентаря, по аналогии с ADR-0004 §3:

- `postgresql_primary` (ровно один хост)
- `postgresql_read_replica` (в том же ДЦ, что и primary; **опциональна** — группа может быть
  пустой, разгрузка чтения не обязательна для всех инсталляций)
- `postgresql_dr_replica` (другой ДЦ Selectel)

Переменная `postgresql_replication_role: primary | read_replica | dr_replica` определяет
ветвление внутри роли (регистрация в `repmgr`, `read_only`-подобные ограничения на уровне
`pg_hba.conf`, источник бэкапа и т.д.), задаётся через `group_vars` на уровне группы.

**Отличие от ADR-0004:** DR-реплика здесь не исключена из обслуживания боевого чтения полностью
(см. §6) — она используется как read-источник в fallback-сценарии, а не только вручную в момент
promote.

### 4. Репликация — physical streaming + repmgr, без автоматического failover

**Решение:** физическая streaming replication (WAL), топология «звезда» (обе реплики
подключаются к primary напрямую, как и в ADR-0004 §4), управление кластером — через `repmgr`
(регистрация узлов `repmgr standby register`, клонирование `repmgr standby clone`,
`repmgr cluster show` для диагностики).

`repmgrd` (демон мониторинга/автоматического failover) **не поднимается в режиме автоматического
failover**. Он либо не запускается вовсе, либо (если понадобится для наблюдаемости) — только в
режиме мониторинга без `failover=automatic`. Переключение — исключительно ручное, по written-
инструкции, тем же оператором, тегами `postgresql_replication_promote` + `never` (см. §7) — тот
же принцип, что и в ADR-0004 §7 (там же прецедент тегов `init`/`never` для `xanmanning.k3s`).

Репликационный пользователь и пользователь `repmgr` — отдельные, с минимальными правами
(`REPLICATION` для первого, `SUPERUSER` для `repmgr` — требование самого repmgr), пароли —
обязательные переменные без дефолта (см. §9).

Обе реплики: доступ только на чтение обеспечивается штатным механизмом PostgreSQL (реплика в
режиме `recovery` физически не принимает записи, в отличие от MySQL, где `read_only`/
`super_read_only` нужно выставлять явно) — отдельного флага не требуется.

### 5. Шифрование трафика репликации между ДЦ

**Решение:** идентично ADR-0004 §5 — роль **не поднимает VPN** и не настраивает PostgreSQL-native
SSL для репликации между ДЦ. МежДЦ-трафик идёт через уже существующий WireGuard/IPsec-туннель,
`postgresql_replication_primary_host` DR-реплики указывает на приватный/туннельный адрес primary,
не публичный. То же предположение (не проверяется `assert`, документируется в README как явная
предпосылка) и то же обоснование: связность между ДЦ уже эксплуатационно обеспечена.

### 6. Единая точка подключения: DNS → Odyssey, включая fallback-чтение с DR

**Решение:** та же схема, что и в ADR-0004 §6(DNS указывает на пулер, не напрямую на серверы БД),
с одним архитектурным отличием от MySQL/ProxySQL, важным из-за особенностей Odyssey.

**Ограничение Odyssey, которое определяет дизайн:** в отличие от ProxySQL, Odyssey не разбирает
SQL и не делает per-query маршрутизацию `SELECT` vs остальное по содержимому запроса — маршрут
определяется на этапе **подключения** (конфигурация `database`/`route` в `odyssey.conf`, у
каждого route — один backend). Поэтому, как и для MySQL, разделение чтение/запись выполняется на
уровне двух разных точек подключения:

- `db-write.<zone>` → route на **primary** — приложения пишут туда;
- `db-read.<zone>` → route на **read-источник для чтения** — приложения читают оттуда.

**Read-источник для чтения — определяется составом инвентаря на момент прогона роли, не
рантайм-переключением внутри Odyssey:**

- если группа `postgresql_read_replica` непустая — `db-read` route в Odyssey указывает на неё;
- если группа `postgresql_read_replica` пустая — `db-read` route указывает на
  `postgresql_dr_replica` (fallback), несмотря на межДЦ-задержку — лучше читать оттуда, чем не
  разгружать primary вовсе.

Это **не** живое автоматическое переключение при отказе read-реплики во время работы — то
противоречило бы принципу «никакой автоматики поверх ручного failover» (§4). Смена
read-источника — результат применения роли с другим составом инвентаря (или ручной правки
`group_vars` + повторного прогона), а не самостоятельное решение Odyssey/repmgr в рантайме.

Odyssey — **отдельные выделенные хосты**, установка нативным пакетом `odyssey` из
**apt.postgresql.org (PGDG)** — того же apt-источника, что уже используется для самого
PostgreSQL, тем же `signed-by`-keyring, без сборки из исходников и без docker. Один
источник пакетов на обе цели (`postgresql-<version>` и `odyssey`) — меньше поверхность
обслуживания репозиториев, чем при отдельном apt/PPA-источнике или сборке на хосте.
**Оговорка:** версия `odyssey` не закрепляется дословно переменной (в отличие от MySQL/PostgreSQL,
где версия фиксируется явно) — ставится, что актуально в PGDG на момент прогона; принимается как
осознанный компромисс ради простоты, пересмотреть при необходимости строгого пиннинга.

**Действие в `infra_dns`:** не требуется — `record.ttl` для `db-write`/`db-read` уже добавлено в
ADR-0004 §6, переиспользуется без изменений.

### 7. Ручное переключение (promote)

**Решение:** идентично ADR-0004 §7 по духу — переключение управляемое, но **ручное**. Механизм —
задачи роли `postgresql_replication` за тегами `postgresql_replication_promote` + `never`.

Задача promote (запускается оператором вручную на хосте DR- или read-реплики, по инструкции):
`repmgr standby promote`. Переподключение остальных узлов к новому primary (`repmgr standby
follow`), обратное переключение (failback) на исходный primary и переключение backend'ов Odyssey
на новый primary/read-источник — отдельные шаги той же written-инструкции, не автоматизируются
полностью.

**Реализовано:** письменная пошаговая инструкция на русском —
`docs/runbooks/postgresql-failover.md` (по аналогии с `docs/runbooks/mysql-failover.md`),
содержит точные `ansible-playbook ... --tags ... --limit ...` команды и ручные `repmgr`/SQL-команды
для шагов, которые роль намеренно не автоматизирует.

### 8. Бэкапы

**Решение:** физический бэкап через **pgBackRest** (де-факто стандарт для PostgreSQL, инкрементальные/
дифференциальные бэкапы + WAL-archiving из коробки), устанавливается из того же PGDG apt-репозитория.

**Источник бэкапа — DR-реплика** (`postgresql_replication_backup_source_role: dr_replica`,
переопределяемо) — тот же принцип, что и в ADR-0004 §8: не создаёт дополнительной нагрузки ни на
primary, ни на read-реплику. Учитывая, что DR-реплика теперь ещё и обслуживает fallback-чтение
(§6), это сознательный компромисс — в fallback-режиме DR несёт и чтение, и бэкап одновременно;
не пересматривается сейчас (нагрузка бэкапа не считается конфликтующей с чтением при текущих
объёмах, пересмотреть при реальных проблемах производительности).

**Доставка в S3:** через **встроенный S3-driver pgBackRest** (`repo1-type=s3`,
`repo1-s3-endpoint`/`repo1-s3-bucket`/`repo1-s3-key`/`repo1-s3-key-secret` — Selectel S3-совместимый
эндпоинт), а не через `rclone`, как в ADR-0004 §8 для MySQL — в отличие от `xtrabackup`,
`pgBackRest` уже имеет нативную интеграцию с S3-совместимыми хранилищами, добавлять `rclone` как
промежуточное звено избыточно.

**Ретеншн — через нативные политики pgBackRest**, а не через префиксы объектов и отдельную задачу
удаления (как в ADR-0004 §8 для rclone): `repo1-retention-full` (число full-бэкапов) +
`repo1-retention-diff` (число diff-бэкапов между full), настраиваемые переменными роли. WAL
сегменты, ставшие ненужными после экспирации бэкапа, `pgBackRest` удаляет сам (`expire`).

Шифрование бэкапов at rest — **не требуется** (тот же явный ответ, что и для MySQL в ADR-0004 §8).

**Алерт «бэкап не создался»:** задача бэкапа по завершении пишет метрику через
textfile-коллектор `node_exporter` (`/var/lib/node_exporter/textfile_collector/postgresql_backup.prom`,
метрика `postgresql_backup_last_success_timestamp_seconds`) — тот же паттерн, что и в
ADR-0004 §8 для `mysql_backup_last_success_timestamp_seconds`. Композиция с `monitoring_agent` —
на уровне инвентаря/плейбука, не meta-зависимость (см. §11).

**Отставание/разрыв репликации:** новый экспортёр `postgres_exporter`
(`prometheus-community/postgres_exporter`) экспортирует `pg_replication_lag_seconds` из коробки
(запрос к `pg_stat_replication`/`pg_last_wal_receive_lsn` и т.п.). Порог алерта на отставание —
**300 секунд**, тот же порог, что и для MySQL в ADR-0004 §8 (нет оснований для другого значения
при сопоставимой нагрузке). Алерт на разрыв — `pg_stat_replication` пуст на primary там, где
ожидается N реплик, либо `pg_replication_is_replica` меняется неожиданно.

### 9. Секреты

**Решение:** пароли (пользователь репликации, пользователь `repmgr`, S3 access/secret key для
`pgBackRest`) — переменные без дефолтов в `defaults/main.yml`, значения — в Ansible Vault на
уровне inventory (`group_vars/<group>/vault.yml`), тот же fail-fast `assert`-паттерн, что и в
ADR-0004 §9 / ADR-0001 §5. Vault уже используется в коллекции с прецедента ADR-0004 — для этой
роли ничего нового вводить не нужно, README документирует то же самое (`ansible-vault encrypt
group_vars/postgresql_primary/vault.yml`).

### 10. Molecule-тестирование — vagrant/libvirt

**Решение:** новый сценарий `extensions/molecule/postgresql_replication/`, тот же
`driver`/провайдер, что и в ADR-0004 §10 (`molecule-plugins[vagrant]` + libvirt) — то же
обоснование: полноценный многоузловой кластер с устойчивым состоянием диска и systemd удобнее
проверять на ВМ, чем в контейнерах. Сценарий поднимает минимум три ВМ
(primary/read_replica/dr_replica), converge прогоняет обе ветки (primary/adopt и replica/fresh
install), verify проверяет `repmgr cluster show` и реальную репликацию (запись на primary,
чтение на репликах). Зависимость `molecule-plugins[vagrant]` в `pyproject.toml` — уже добавлена
для `mysql_replication`, переиспользуется без изменений.

Отдельный сценарий для `odyssey` — `driver: docker` (как `nginx_multidomain`/`reverse_proxy_npm`),
так как это одиночный stateless-сервис без требований к устойчивому диску/нескольким узлам.

### 11. Взаимодействие с существующими ролями — только композиция, не meta-зависимости

**Решение:** идентично ADR-0004 §11 — ни `postgresql_replication`, ни `odyssey` не объявляют
`dependencies` на `monitoring_agent`/`infra_dns` в `meta/main.yml`. Хосты получают
`monitoring_agent` тем же способом, что и остальные роли коллекции — через плейбук оператора.

## Открытые вопросы / вне скоупа

- **Alertmanager (ROADMAP P0 №1) не работает** — та же оговорка, что и в ADR-0004: алерты этого
  ADR технически не дойдут до оператора, пока P0-баг не закрыт отдельной работой.
- Автоматический failover — исключён явно (см. §4), не рассматривался и не будет рассматриваться
  в рамках этой архитектуры.
- Несколько read-реплик одновременно (сейчас — ровно одна, группа опциональна) — инвентарная
  модель (§3) допускает расширение, но балансировка между несколькими read-репликами в Odyssey не
  проектировалась.
- Версия `odyssey` не закреплена жёстко (см. §6) — берётся текущая из PGDG; пересмотреть, если
  потребуется строгий пиннинг версии пулера.
- RHEL/Rocky — вне scope, как и во всей коллекции (ADR-0002 §4).
- Поднятие самого WireGuard/IPsec-туннеля между ДЦ — вне scope (см. §5), связность считается
  предоставленной внешне (то же допущение, что в ADR-0004 §5).
- Шифрование бэкапов at rest в S3 — явно не требуется (см. §8), пересмотреть при изменении
  требований по комплаенсу.
- Совмещение чтения и бэкапа на DR-реплике в fallback-режиме (§8) — принято как компромисс без
  дополнительной защиты; пересмотреть при реальных проблемах производительности.
