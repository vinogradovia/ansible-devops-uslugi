# ADR-0023: Роль `postgresql` (standalone-сервер для нужд платформы)

- **Статус:** Принято
- **Дата:** 2026-09-07
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

Платформенным компонентам (LiteLLM, Grafana, в перспективе другим) нужна общая БД. LiteLLM
работает в config-only режиме без БД (явно отложено в ADR-0015 §7 — "ns: data ещё не развёрнут"),
Grafana использует встроенный sqlite. Запрошен **отдельно стоящий (не кластерный) Postgres-сервер**
для этих нужд, в обоих платформенных окружениях (`platform/aicd`, `platform/aicd-devops-labs-ru`).

Единственная существующая в коллекции Postgres-роль — `roles/postgresql_replication`
(`docs/adr/0005-postgresql-ha-replication-role.md`) — рассчитана исключительно на HA (`repmgr`,
обязательные replication-переменные, 3-узловая топология в molecule) и не имеет режима standalone.
ADR-0015 §"Схема размещения" уже называет `postgres+pgvector (cnpg)` как решённую архитектуру для
`ns: data` агентного стека (CloudNativePG-оператор в k3s) — но этот компонент решает другую задачу
(retriever/pgvector контур для агентов), и для текущего запроса (платформенная БД общего
назначения) осознанно выбран другой путь: отдельная VM с systemd, не k8s.

## Решения

### 1. Новая роль, не расширение `postgresql_replication`

**Решение:** `roles/postgresql` — отдельная роль, не режим существующей `postgresql_replication`.

**Обоснование:** реально общий код между HA и standalone — только PGDG apt-репозиторий и установка
пакета (~40-60 строк). TLS в `postgresql_replication` не существует вовсе (ADR-0005 §5 сознательно
полагается на доверенную приватную сеть, а не шифрование канала) — новый код в любом случае.
Расширение потребовало бы: `when`-условий на каждую обязательную HA-переменную в
`assert-required-vars.yml`, разделения `configure-postgresql.yml` (сейчас один файл мешает
`wal_level`/repmgr-preload/`pg_hba` вместе) на generic/repmgr-specific части, нового `when` в
`tasks/main.yml` вокруг безусловной установки `repmgr`/pgBackRest — правки в общих файлах уже
проверенной (`molecule test` зелёный) HA-роли, потенциально боевой (`demo/postgresql-ha-platform`),
с риском регресса HA-пути. Существующий molecule-сценарий (3 ВМ + Bareos, `verify.yml` целиком про
`repmgr cluster show`/promote) не годится для standalone-ветки как есть — реально всё равно нужен
отдельный сценарий, то есть выгода от переиспользования molecule умозрительна. Плюс семантическая
путаница: `postgresql_replication_role: standalone` внутри роли, которая называется `_replication`.
Прецедент уже есть в коллекции — `mysql_replication` существует отдельно, без "standalone"-режима
внутри, то есть принцип "роль = одна топология" не изобретается сейчас, а продолжает уже принятый
подход.

### 2. Топология — отдельная VM с systemd, не CNPG/k8s

**Решение:** роль ставит PostgreSQL как обычный systemd-сервис из PGDG apt на выделенную VM —
не CloudNativePG-оператор в k3s, несмотря на то, что этот путь уже описан в ADR-0015 для `ns: data`.

**Обоснование:** явный выбор пользователя после сравнения обоих вариантов. `ns: data`/CNPG решает
задачу retriever/pgvector контура агентного стека (ADR-0015 §"Схема размещения") — другой компонент
с другим назначением; платформенная БД общего назначения (litellm/grafana/и т.п.) не обязана жить
в той же архитектуре.

### 3. Границы ответственности роли — только движок, не БД/пользователи-потребители

**Решение:** роль устанавливает и настраивает PostgreSQL (engine, TLS, базовый `pg_hba.conf`) —
**не** создаёт БД/пользователей-потребителей (litellm, grafana и т.п.) и не принимает переменную
вида `postgresql_databases`. Заведение конкретного потребителя — ad hoc на уровне playbook'а через
`community.postgresql.postgresql_db`/`postgresql_user`/`postgresql_pg_hba`.

**Обоснование:** это уже действующая в коллекции конвенция — `demo/postgresql-ha-platform/ansible/
site.yml` заводит `postgres_exporter`/`odyssey`-пользователей точно так же, ad hoc, не через
`postgresql_replication`. Композиция на уровне playbook'а, не роли, даёт более точечный контроль
над per-database/per-user грантами (см. §5) и не заставляет роль знать о конкретных потребителях
платформы.

### 4. TLS — самоподписанный сертификат по умолчанию

**Решение:** `postgresql_tls_enabled: true` (default), `community.crypto.openssl_privatekey`/
`openssl_csr`/`x509_certificate` (`provider: selfsigned`) — тот же паттерн, что `roles/fail2ban_ui`
и self-signed TLS для vmsingle/grafana в `monitoring_server` (k3s-путь).

**Обоснование:** в отличие от `postgresql_replication` (ADR-0005 §5 сознательно полагается на
доверенную приватную сеть/VPN без шифрования канала), эта роль всегда шифрует трафик — недорого, и
корректно на случай, если сеть платформы окажется менее доверенной, чем межДЦ-VPN из ADR-0005.

### 5. `pg_hba.conf` — убран Debian-дефолтный catch-all по loopback

**Решение:** роль явно удаляет две строки, которые Debian-пакет `postgresql-common` рендерит в
`pg_hba.conf` по умолчанию: `host all all 127.0.0.1/32 scram-sha-256` и `host all all ::1/128
scram-sha-256`. После роли pg_hba.conf разрешает только `local`/unix-сокет (`peer`) — никакого
сетевого доступа по умолчанию, для любой БД/пользователя.

**Обоснование:** реальная находка живым прогоном molecule (`extensions/molecule/postgresql/`,
verify) — пользователь, заведённый потребителем под одну конкретную БД с точечным `hostssl`-грантом
(§3), всё равно мог подключиться по plain TCP (`sslmode=disable`) к **любой** БД — не через свой
грант, а через этот Debian-дефолтный catch-all (он матчит `all`/`all`, за пределами SSL-требования,
и стоит раньше в файле). Это напрямую противоречило замыслу §3 — точечный, а не транзитивно
широкий доступ. Суперпользователя `postgres` это не касалось и до фикса (роль никогда не назначает
ему пароль, catch-all требует `scram-sha-256`, то есть пароль), но для любого потребителя с
паролем — касалось.

### 6. Naming convention — `postgresql-infra-1`

**Решение:** имя хоста/VM/DNS — `postgresql-infra-1`, формат `<component>-<purpose>-<n>`:
`postgresql` — тип компонента, `infra` — назначение (обслуживает саму платформу, в отличие от
гипотетической БД под конкретный клиентский проект), `1` — номер инстанса (оставляет место для
`postgresql-infra-2` и т.п. без переименования). Разделитель — по соглашению конкретной системы, не
буквально одна и та же строка везде: Terraform/DNS/Semaphore Project — дефис; Ansible-инвентарная
группа — по уже 100%-но принятому в коллекции соглашению `<name>_hosts` через underscore
(`postgresql_infra_hosts`, во множественном числе — в отличие от singleton-групп вроде
`freeipa_hosts`, эта заведомо может содержать больше одного хоста этого назначения в будущем).

**Обоснование:** у платформы до сих пор не было явного naming convention для новых компонентов —
имена выбирались ad hoc для каждого компонента отдельно (`freeipa`, `cicd`, `llm1`). Это первый
компонент, спроектированный с расчётом на потенциальную множественность инстансов с самого начала.
Закрытый список допустимых `purpose` (`infra`/`client-<slug>`/`project-<slug>`) и сам факт
отсутствия общего naming convention зафиксированы отдельным пунктом в `ROADMAP.md` — не оставлять
`purpose` свободной строкой во избежание разнобоя в будущих компонентах.

### 7. Способ применения — Terraform вручную (пока), Ansible через отдельный Semaphore Project

**Решение:** Terraform (`postgresql-infra-target.tf` в обоих окружениях) применяется по-прежнему
вручную (`tofu apply` с подтверждением оператора) — перенос в Semaphore отложен в `ROADMAP.md` до
появления S3-совместимого хранилища на платформе (нужен remote state; сейчас `terraform.tfstate`
лежит локально в каждом `platform/*/terraform/`, а Semaphore обычно клонирует репозиторий заново на
каждый прогон).

Ansible-часть — через новый, отдельный **Semaphore Project** `postgresql-infra` в каждом окружении
(у `aicd` и `aicd-devops-labs-ru` — собственные, независимые инстансы Semaphore), по принципу
"1 проект = 1 компонент" (явно запрошено). Task Template запускается вручную/по требованию — **без**
Module CRD/автоматического drift-reconcile (`docs/adr/0014-platform-controller-architecture.md`
§3 сам называет автоматическое переприменение раз в 30 сек плохо сочетающимся со stateful-ролями,
где рестарт боевой БД требует согласованного окна — тот же принцип, что уже действует для
`postgresql_replication_allow_restart` в HA-роли).

**Task Template ограничен полем `Limit` = `postgresql-infra-1`, не вся группа
`postgresql_infra_hosts`.** Группа во множественном числе (§6) — если позже в ней появится
`postgresql-infra-2`, безусловный прогон плейбука на всю группу задел бы оба инстанса разом одним
запуском. Каждый новый инстанс получает свой собственный Task Template (свой `Limit`) явным шагом,
а не наследует чужой автоматически через членство в общей группе.

**Ограничение окружения выполнения:** содержимое для `platform/gitops`/`platform/devops-uslugi`
(wrapper-плейбук `playbooks/postgresql-infra.yml`, инвентарная запись) готовится агентом как
контент, но `git push` в эти репозитории агенту недоступен — инструментарий безопасности расценивает
это как передачу содержимого доверенного репозитория и блокирует независимо от согласия
пользователя (та же причина, по которой зеркало `devops-uslugi` для пилота `infra_panel` пользователь
пушил вручную, см. `platform/aicd/README.md`, «Ручные шаги»). Пуш делает пользователь.

### 8. Явные решения по чек-листу ADR-0022

- **№1 (внутренний Nexus)** — apt PGDG репозиторий, не Nexus (тот же статус, что у
  `postgresql_replication`/остальной коллекции — известный, не блокирующий для этого захода пробел).
- **№9 (resources)** — н/п в этой форме (VM, не k8s pod); ёмкость VM — фиксированный vCPU/RAM в
  terraform.
- **№10 (NetworkPolicy)** — н/п буквально (не k8s workload); эквивалент — `pg_hba.conf` ограничивает
  доступ per-database/per-user по CIDR платформенной сети (§5), суперпользователь `postgres` не
  слушает внешние подключения вовсе.
- **№11 (backup)** — **явно отложено**. Bareos-механизм существует (`backup_agent` роль,
  `backup_agent_install_postgresql_plugin` тумблер уже есть), но `backup_server` для платформы нигде
  не развёрнут (ADR-0022 сам фиксирует: 0 существующих компонентов платформы зарегистрированы в
  Bareos) — поднимать `backup_server` ради одной БД вне утверждённого сейчас скоупа. Осознанное
  "не сейчас", зафиксировано в `ROADMAP.md`, а не тихий пробел.
- **№12 (MCP)** — н/п (Postgres не MCP-потребитель и не поставщик).

## Открытые вопросы / вне скоупа

- Создание БД/пользователей `litellm`/`grafana` (даже "заготовкой впрок"), переключение LiteLLM на
  БД, миграция Grafana с sqlite на Postgres — явно вне скоупа этого захода (уточнено пользователем
  отдельно). У Grafana уже есть живые dashboard'ы в sqlite — переключение на Postgres не мигрирует
  их автоматически, требует отдельного решения.
- Naming convention для платформенных компонентов (§6) — зафиксирован только формат и первый
  пример, сам процесс согласования (кто и когда решает, что использовать) не описан.
- Перенос Terraform-apply в Semaphore (§7) — заблокирован на появлении S3-компонента для remote
  state, отдельный пункт `ROADMAP.md`.
- Зеркалирование `ghcr.io`/дополнительных источников через Nexus (№1) — тот же известный пробел, что
  уже заведён в `ROADMAP.md` через LiteLLM-аудит (№59), не специфичен для этой роли.
