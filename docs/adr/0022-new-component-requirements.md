# ADR-0022: Требования к новым компонентам платформы (чек-лист онбординга)

- **Статус:** Предложено (архитектурное решение; реализация не начата)
- **Дата:** 2026-09-06
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

Платформа (`platform/aicd`, `platform/aicd-devops-labs-ru`) выросла до девяти Helm-релизов и
одного кластерного стека (ADR-0015-0018, ADR-0021), каждый добавлялся отдельным ADR, и каждый раз
заново передоказывались одни и те же вопросы: откуда брать образ/чарт, как заводить TLS, как
защищать вход, куда положить пароль. Часть ответов совпадала (PKI CA, OpenBao, htpasswd), часть
плыла от компонента к компоненту. Нужен стандарт, применяемый **до** написания декларации нового
компонента, а не выводимый постфактум из того, что получилось.

**Область действия.** Требования ниже — для **новых** компонентов, добавляемых начиная с этого
ADR. Уже существующие (`gitea`, `semaphore`, `openbao`, `radar`, `infra-panel`, `nexus`,
`authelia`, стек `vm`/`grafana-operator`/`loki`) не обязаны ретроактивно соответствовать —
конкретные несовпадения перечислены явно в каждом пункте («Известное исключение»), а не
замалчиваются.

## Требования

### 1. Установка из внутреннего репозитория; интернет — только явный, задокументированный fallback

**Механизм уже частично существует (ADR-0018) — не изобретается заново:**

| Тип артефакта | Внутренний источник | Механизм |
|---|---|---|
| Docker/OCI-образ | `nexus-cache.<домен>` (`docker` proxy repo) | `registries.yaml` mirror на каждом k3s-узле, нативный механизм containerd |
| k3s-бинарь + checksum | `nexus-cache.<домен>` (`raw` proxy repo) | override `k3s_binary_url`/`k3s_hash_url` у `xanmanning.k3s` |
| apt-пакеты (`nvidia-container-toolkit`, gVisor) | `nexus-cache.<домен>` (`apt` proxy repo) | source-list переписывается опциональной переменной; при 401/недоступности — `block`/`rescue` на прямой источник (уже реализовано в `roles/k3s_gpu_node`) |
| Собственные бинарные артефакты (например, `freeipa_exporter`) | `internal-releases` (raw hosted repo) | ADR-0018 §9 |

**Блокирующий пробел — решено закрыть до следующего компонента, не принимать как исключение.**
ADR-0018 §3 прямо откладывает `helm`-формат на следующую итерацию — сегодня **все** Helm-релизы
платформы (`openbao`, `gitea`, `semaphore`, `radar`, `infra-panel`, весь monitoring-стек)
тянут чарт напрямую из публичного интернета безусловно, не как fallback, а как единственный путь.
Формально это означает, что требование №1 сегодня не выполняется ни одним существующим
Helm-релизом. **Решение:** Nexus получает `helm` proxy-repo (формат уже поддержан, просто не
включён — ADR-0018 §3), существующие Helm-репозитории платформы переключаются на него **до** того,
как в `helm/envs/platform.yaml`/`helm/envs/platform-devops-labs-ru.yaml` добавляется следующий
новый релиз. Компонент, добавленный в обход этого (чарт напрямую из публичного репо, без прохода
через `nexus-cache`), считается нарушающим требование №1, а не законным исключением — в отличие
от существующих релизов, добавленных **до** этого ADR.

**Обоснование:** fallback уже реализован именно как «rescue», не как молчаливое поведение —
apt-пример выше логирует, что кеш недоступен, и явно откатывается, а не тихо ходит в интернет
всегда. Это и есть форма, в которой должно быть реализовано «допускается fallback при bootstrap»:
видимый, а не default-режим.

### 2. RBAC сразу — через групповую модель ADR-0019/0020, не через shared-пароль

**Уточнение механизма:** «сразу» означает конкретный, уже спроектированный путь, не абстрактный
OAuth/LDAP:
- **Веб-UI без нативного OIDC** (как сейчас `infra-panel`/Traefik dashboard) — `forwardAuth` на
  Authelia, `access_control.rules[].subject: ['group:platform-...']` (ADR-0019 §5), не
  безусловный `policy: one_factor` без условия на группу.
- **Веб-UI с нативным OIDC** (как `gitea`/`semaphore`/`grafana`) — клиент Authelia +
  `authorization_policies` + claim `groups` в ID Token (ADR-0019 §4-5), маппинг persona→роль
  внутри сервиса (ADR-0019 §6).
- **kube-apiserver**, если компонент требует прямой доступ к кластеру — ADR-0020, префикс `oidc:`.

**Переходное решение — до реализации ADR-0019/0020.** Оба сами ещё в статусе «Предложено»: групп
в каталоге нет, `claims_policies` для `groups` не заведены, `freeipa_directory` не существует.
Требовать полноценный OAuth/LDAP-групповой RBAC от следующего компонента раньше, чем это будет
готово, остановило бы развитие платформы ради требования, которое физически нечем выполнить.
**Решение:** до тех пор новые компоненты используют тот же паттерн, что уже применён для
`radar`/`infra-panel` — `forwardAuth` + общий htpasswd-пароль (ADR-0017 §2-3). Это не нарушение
требования №2, а его временная реализация. **Обязательное условие перехода:** как только
ADR-0019/0020 реализованы, каждый компонент, добавленный в переходный период на shared-пароле,
обязан быть переведён на групповую модель — это не остаётся исключением навсегда, в отличие от
компонентов, добавленных до этого ADR.

**Известное исключение (только для компонентов ДО этого ADR):** `radar`, `infra-panel`
(shared basic-auth), `openbao` (свой root token/policy, аутентификация не переиспользуется
вовсе) — ретрофит для них решается отдельно и не покрывается автоматически «обязательным условием
перехода» выше (то условие — только для компонентов, добавленных уже после этого ADR).

### 3. Ссылка в `infra-panel`

Без изменений от очевидного — новая запись в конфиге `homer` (`infra_panel_extra_services` или
эквивалент для `platform/aicd*`), тот же список, что уже включает Gitea/Semaphore/Radar/OpenBao
(ADR-0017 §3). Дёшево, но легко забыть — именно поэтому фиксируется отдельным пунктом чек-листа,
а не полагается на память.

### 4. Метрики — экспортёр, scrape, дашборд, все три сразу

**Механизм уже есть, но состоит из двух независимых половин, которые исторически расходились:**
ADR-0017 §5 прямо документирует случай, когда `ipa_exporter` был подключён к скрейпу
(`VMScrapeConfig`), но дашборда не было вообще — «половина работы была сделана, вторая — нет»,
обнаружено жалобой оператора, а не проверкой.

**Уточнение требования: три части сдаются вместе, в одном PR/прогоне, не по отдельности:**
1. Экспортёр (или встроенные `/metrics`, если сервис их отдаёт нативно) — цель `VMScrapeConfig`.
2. Скрейп реально подтверждён `curl :<port>/metrics` **и** видимостью серии в VictoriaMetrics —
   не «конфиг применён», а «данные пришли».
3. Дашборд — `GrafanaDashboard` CR из `ADDONS/grafana_dashboards/*.json` (ADR-0017 §5), с
   заменёнными плейсхолдерами `${DS_...}`, а не голый JSON без datasource.

### 5. TLS — из внутреннего PKI CA, тем же циклом, что у всех остальных

**Решение:** любой веб-эндпоинт нового компонента получает сертификат из уже существующего цикла
`tasks/issue-tls-cert.yml` (OpenBao PKI, ADR-0016) — компонент добавляется как ещё один элемент
существующего `loop`, не отдельным механизмом.

**Обоснование:** это уже происходило три раза подряд без исключений (`gitea-tls`, `semaphore-tls`,
`radar-tls`, `infra-panel-tls`, `openbao-ingress-tls` — ADR-0017 §2-3) — устоявшийся паттерн,
явно фиксируется, чтобы не переизобретался в пятый раз.

### 6. DNS — запись в двух местах, не в одном

**Решение:** новый домен компонента (`<name>.aicd.platform` и т.п.) заводится **одновременно**
в двух местах:
1. `coredns-custom` ConfigMap кластера — резолвинг **внутри** пода (нужен, если что-то в кластере
   обращается к домену компонента, не только браузер оператора снаружи).
2. README окружения, раздел «/etc/hosts операторов» — резолвинг для человека и для нод вне
   кластера (`llm1` — характерный пример, ADR-0015 §10).

**Обоснование:** это единственный класс проблемы, который находили заново **минимум четыре раза**
в разных ADR — `sso.aicd.platform` для Gitea/Semaphore (ADR-0013 §7), `gitea.aicd.devops-labs.ru`
и `nexus-cache.aicd.devops-labs.ru` для `llm1` (ADR-0015 §10, ADR-0018), — каждый раз с одинаковым
симптомом («no such host») и одинаковым решением. Стоит закрыть чек-листом, а не находить в пятый
раз реальным прогоном.

### 7. Секреты — идемпотентно из OpenBao, никогда не в values/git

**Решение:** пароль/токен нового компонента генерируется/читается идемпотентным
GET→404→POST-циклом в `secret/<component>` OpenBao (тот же приём, что `secret/nexus`/
`secret/radar`/`secret/gitea`, ADR-0016 §3), подставляется в values через `gomplate`
`vault://`-datasource. Ни один пароль не появляется как plaintext в git.

**Обоснование:** уже устоявшийся паттерн без единого исключения среди существующих компонентов —
формализуется, а не вводится заново.

### 8. Обязательный стаб `helm/values/releases_common/<name>.yaml`

**Решение:** для каждого нового Helm-релиза заводится (пусть пустой, `---`) файл
`helm/values/releases_common/<name>.yaml` **до** первого `helmwave up`.

**Обоснование:** конкретная, дважды наступленная операционная грабля — `helmwave.yml.tpl` требует
этот файл в `strict: true`-режиме для **каждого** релиза; забытый файл роняет прогон с
`values file doesn't exist` (найдено при добавлении `infra-panel`, ADR-0017 §3). Дешевле включить
в чек-лист, чем находить заново на каждом новом релизе.

### 9. Явные `resources.requests`/`limits`

**Решение:** новый компонент декларирует explicit `resources.requests`/`limits`, не полагается на
дефолт чарта (который у многих чартов вообще не установлен).

**Обоснование — не гипотетическое:** из девяти существующих релизов явные лимиты на момент
написания были выставлены только у четырёх (`nexus`, `vmsingle`, `grafana-operator`, `vm`) —
остальные (`gitea`, `semaphore`, `radar`, `infra-panel`, `openbao`, `authelia`) шли без
ограничений вообще. На единственной ноде с уже как минимум однажды случившимся дефицитом памяти
(`llm1`, ADR-0021 §3 — 10 ГБ реальной RAM оказалось недостаточно для того, что на неё пытались
посадить) необъявленный лимит — не нейтральная настройка, а риск, что один компонент съест память
соседа без предупреждения.
**Известное исключение:** `semaphore`, `radar`, `infra-panel`, `openbao`, `authelia`. Ретрофит —
отдельная задача. `gitea` из списка исключений выведен (2026-09-06) — получил явные
`resources.requests`/`limits` заодно с добавлением `gitea-actions-runner` (§12 ниже), который
сразу декларирует свои лимиты как новый компонент.

### 10. NetworkPolicy — явное решение обязательно, `default-deny` не требуется по умолчанию

**Решение:** при добавлении нового компонента его namespace (новый или существующий) явно
рассматривается на предмет NetworkPolicy, и результат — `default-deny` с allowlist, более узкое
правило, или осознанное «не нужно» — фиксируется в ADR/комментарии компонента. Молчаливое
отсутствие решения (как сейчас у всех namespace, кроме `agents`) не допускается для новых
компонентов.

**Обоснование:** `default-deny` сегодня есть только в `ns: agents` (ADR-0015 §7) — там, где
компрометация одного пода (песочница агента, исполняющая произвольный код) особенно дорога.
Требовать ту же тяжёлую модель для простого read-only UI-дашборда (как `radar`) было бы
неоправданным по стоимости эксплуатации без соразмерной выгоды — но и отсутствие любого решения
(текущее состояние `platform`/`monitoring`/`cache`) означает, что вопрос просто не был задан.
Требование — задать вопрос и записать ответ, не обязательно ответить «да» на default-deny.
**Известное исключение:** `platform`, `monitoring`, `cache` — решение не принималось; закрывается
отдельно, не этим ADR.

### 11. Резервное копирование — явное решение при добавлении stateful-компонента

**Решение:** любой новый компонент с состоянием, потеря которого некритична не сразу, а
болезненна (репозитории Gitea, проекты Semaphore, секреты/политики OpenBao, данные Nexus) при
добавлении явно решает: регистрируется ли он в `backup_server_clients`/`backup_server_filesets`
(Bareos, ADR-0009/0010, уже реализован и проверен на `demo/backup`), или нет — с явно записанной
причиной, если нет (например, «состояние воспроизводимо из GitOps, бэкап избыточен»).

**Обоснование — не гипотетическое:** сегодня **ни один** компонент платформы не зарегистрирован
в Bareos — ни Gitea, ни Semaphore, ни OpenBao, ни Nexus. Механизм существует и проверен на другом
классе нагрузки (`demo/backup`, `postgresql_replication`/`mysql_replication` через
`_backup_tool: bareos`), но ни разу не был даже рассмотрен для платформенных сервисов — это не
осознанный выбор «бэкап не нужен», а то, что вопрос никогда не задавался. Требование — не
«бэкапь всё», а «явно реши и запиши», чтобы дыра не воспроизводилась молча в десятый раз.
**Известное исключение:** все существующие stateful-компоненты платформы — решение не принималось
ни для одного; закрывается отдельной задачей (кандидат в ROADMAP), не этим ADR.

### 12. MCP — регистрируется сразу, если для компонента уже есть готовая реализация

**Решение:** при добавлении нового компонента проверяется, существует ли для него официальный
(от вендора) или зрелый community MCP-сервер. Если да — он регистрируется в `mcp_servers:`
LiteLLM (тот же `config.yaml`, что `model_list`, ADR-0015 §6/§7 — не отдельный продукт: `LiteLLM
proxy` уже имеет встроенную MCP-поддержку, `mcp-context-forge`/`microsoft/mcp-gateway`
рассмотрены и отклонены) в рамках того же PR/прогона, что добавляет сам компонент — не
откладывается на «потом».

**Что считается «готовой реализацией», а что нет:** официальный сервер вендора (публикуется в
организации/репозитории самого продукта) или явно поддерживаемый community-проект — не первый
результат поиска. Для уже развёрнутых компонентов это реально существует: официальный
[`grafana/mcp-grafana`](https://github.com/grafana/mcp-grafana) (Apache-2.0, доступ к
дашбордам/датасорсам/Prometheus/Loki/алертам) и официальный
[`gitea/gitea-mcp`](https://gitea.com/gitea/gitea-mcp) (образ
`docker.gitea.com/gitea-mcp-server`, доступ к репозиториям/issues/PR). Если ни официального, ни
поддерживаемого community-варианта нет — писать MCP-обёртку с нуля **не входит** в это требование:
это отдельная задача уровня ADR-0015 §9 (шаг 9, первый реальный MCP-инструмент-бэкенд), не
онбординг компонента.

**Регистрация — не то же самое, что доступ.** Появление сервера в `mcp_servers:` делает
инструмент видимым гейтвею, но не выдаёт его автоматически всем пяти агентам — какой агент какой
инструмент получает, по-прежнему решает специализация ADR-0015 §3 («один агент — один слой
инструментов»), а сам вызов проходит через аудит/allowlist гейтвея (§7). Регистрация — необходимое,
но не достаточное условие использования.

**Обоснование — не гипотетическое, а уже упущенная возможность:** `mcp_servers: {}` в уже
развёрнутом LiteLLM-гейтвее (2026-09-06, ROADMAP №57) сегодня пуст, хотя оба уже работающих на
платформе компонента, для которых официальный MCP-сервер существует (Grafana, Gitea), были
добавлены раньше и без этого шага — не потому что было принято решение не подключать, а потому
что вопрос не задавался на момент их добавления. Тот же класс проблемы, что требование №4
(экспортёр без дашборда) — работа сделана наполовину, а не решение оставить как есть.
**Известное исключение:** `grafana-operator`, `gitea` — оба добавлены до этого ADR без проверки
на существование готового MCP-сервера; регистрация обоих — дешёвая отдельная задача (сервер уже
существует и поддерживается вендором), но не блокирует новые компоненты и не входит в этот ADR.

### 13. Документация — `docs/platform/<name>.md` заводится сразу, актуализируется при каждом изменении

**Решение:** при добавлении нового компонента платформы одновременно (в том же PR/прогоне, что сам
компонент) заводится `docs/platform/<name>.md` — HLD/LLD/DD по уже устоявшемуся шаблону
(`docs/platform/README.md`), не откладывается на «потом». При каждом последующем архитектурном
изменении компонента (новая зависимость, смена паттерна доступа, решение по TLS/секретам/
NetworkPolicy/бэкапу и т.п.) — соответствующий раздел файла обновляется в том же PR/прогоне, что и
сам код/values, а не отдельным «догоняющим» проходом.

**Обоснование — не гипотетическое, а то, что уже произошло.** До 2026-09-07 все 14 компонентов
k3s-платформы (`gitea`, `semaphore`, `openbao`, `radar`, `infra-panel`, `nexus`, `authelia`,
`freeipa`, monitoring-стек, `flux`, `platform-controller`, `gitea-actions-runner`,
`agent-platform`) существовали без единого выделенного архитектурного документа — только ROADMAP/
ADR/README, ни одного целостного HLD/LLD/DD ни по одному из них. Закрывать разрыв пришлось одним
ретроактивным проходом сразу по всем 14 файлам, а не постепенно, вместе с добавлением каждого
компонента — тот же класс проблемы, что уже описан требованием №4 (метрики без дашборда) и №12
(MCP не проверяется при добавлении): часть работы откладывается «на потом» и превращается в долг,
а не в осознанное решение «документация не нужна». Разница с №4/№12 — здесь долг оставался
незамеченным дольше всех и накопился по всей платформе разом, а не по одному компоненту.

**Известное исключение (только для компонентов ДО этого требования):** все 14 существующих
компонентов получили `docs/platform/<name>.md` ретроактивно, одним проходом 2026-09-07 (не в
рамках их первоначального PR) — сам этот факт не нарушение (документы созданы до введения
требования), но начиная с этого ADR повторный ретроактивный проход по нескольким компонентам сразу
не считается приемлемым способом закрыть разрыв — документация обязана появляться вместе с
компонентом/изменением, а не отдельным поздним проходом.

**Место публикации.** Файл живёт в git (`docs/platform/`) независимо от того, реализован ли
черновик `docs/adr/0024-platform-docs-site.md` — публикация сайта внутри стенда (если будет
реализована) лишь делает уже существующий git-контент читаемым без доступа к репозиторию, не
заменяет обязанность его писать и поддерживать.
