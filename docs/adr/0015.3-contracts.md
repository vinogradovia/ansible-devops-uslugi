# ADR-0015.3: Контракты lk-api — Intent, Plan, Estate, Inventory

- **Статус:** Предложено (схема объектов; код lk-api не реализован)
- **Дата:** 2026-09-24
- **Авторы:** Alexandr Yankov (решения), Cursor (оформление по итогам обсуждения)

## Контекст

[ADR-0015.1](0015.1-infra-agent.md) задаёт цикл Intent → Plan → Review → Approve, память Estate /
Inventory и оси размещения (`owner` / `procurement` / `connect`). Без полей и статусов меню и
чат расходятся, экраны LK нельзя нарисовать 1:1.

Этот ADR не пересматривает 0015.1 и не описывает platform admin ([0015.2](0015.2-admin-panel.md)).
Только четыре объекта в lk-api. Код, OpenAPI-сервер и `tofu apply` сюда не входят.

## Решения

### 1. Общие правила

**Решение:** объекты живут в lk-api, ключ — `project_id`. Не в контексте чата и не в весах
модели. У каждого: `id`, `revision` (optimistic lock), `updated_at`,
`updated_by` (`client` | `agent` | `system`).

- Open WebUI их не создаёт.
- Секретов в полях нет (ключи — OpenBao, 0015.2 / 0016).
- На Project один активный цикл (Intent + текущий Plan). Второй — отказ, не очередь (0015.1 §3).
- Агент в каждом Run **сначала** читает Estate и Inventory.

**Обоснование:** HITL в 0015 для инфры закрыт объектами lk-api, не `interrupt()` SDK. Без
контракта это нельзя одинаково реализовать в мастере и в чате.

### 2. Intent

Структурированное желание, не промпт. Меню и чат пишут сырые поля; агент нормализует стек,
best-practice, `where[]`, `import[]`. Клиент может снять пункт best-practice; `import[]` — только
через Init (0015.1 §6).

Статусы: `collecting` → `ready` → `locked` (появился первый Plan) → `abandoned`.

```yaml
source: menu | chat | mixed
stack: [dns, postgres, k3s]
where:
  - site_id: plat-pve-1
    owner: platform
    procurement: platform_metal
    connect: local
    provider_id: null
    pattern: P1
    kind: vm
best_practice:
  - {id: monitoring, included: true, source: agent}
import: []          # id из Inventory
repo_ref: null
notes: ""           # не источник правды
```

`where[]` — только опубликованный каталог площадок (0015.2). Смысл `owner` / `procurement` /
`connect` / `pattern` — 0015.1 §9.

### 3. Plan

То, что ревьюят. Версии `vN` не затираются. Статусы: `draft` → `in_review` →
`approved` | `abandoned`; после записи репо — `repo_ready`. `tofu apply` в объект не входит.

Агент создаёт `draft` из Intent + Estate + Inventory. Клиент правит в LK или просит в чате
(снова `draft`), утверждает или закрывает. Чат без Approve Estate не меняет.

```yaml
version: 3
intent_id: ...
diff_from: 2
items:
  - kind: vm
    action: create | import | skip
    depends_on: []
    placement:
      owner: client
      procurement: partner
      provider_id: selectel
      connect: api
      site_id: partner-selectel-spb
      pattern: P3
    module: site-proxmox | TBD
    roles: [devops.uslugi.monitoring_agent]
    rationale: "best-practice monitoring"
    estate_ref: null   # если уже в Estate — не создавать заново
```

Нет модуля — `TBD`, репо не рисует несуществующий provider (0015.1 §9, 0025 §2).

### 4. Estate

Чем **управляем**. Зеркало — tfstate после репо, не Inventory.

Статусы записи: `imported` | `planned` | `in_repo` | `applied` | `released`.

Пишет: Init/import → `imported`; Approve → `planned` затем `in_repo`; будущий Apply-Run →
`applied`. Чат без Approve не пишет. `owner` не выводится из hostname.

```yaml
owner: platform | client
procurement: platform_metal | partner | byo
site_id: plat-pve-1
provider_id: null
name: vm-app-1
kind: vm
status: planned
module_ref: site-proxmox
plan_version: 3
```

Для `owner: platform` в книге Project — только опубликованный срез (`offered`, 0015.2).

### 5. Inventory

Как контур **выглядит**. Не Ansible `inventory.yml` (тот выводится после Approve, 0015.1 §8).

Схема узла — 0015.1 §8 плюс `owner` / `procurement` / `site_id` / `connect`. Наше железо в книге
Project — только опубликованный срез, каждый узел с `owner: platform`.

`meta.completeness`: `placement` | `placement+guest` | `full`. Пишет только agent tool (Init,
сверка). Клиентский import — это `Intent.import[]`, не правка фактов.

После Approve — зеркало в клиентский git (`inventory/facts.yml`) рядом с
`ansible/inventory.yml`.

## Кто пишет

| Объект | Клиент LK | Агент | Platform admin (0015.2) |
|---|---|---|---|
| Intent | сырые поля меню/чата; снять best-practice; Approve не здесь | нормализует | нет |
| Plan | правки, Approve, закрыть | `draft` / `vN+1` | нет |
| Estate | нет (кроме выбора import через Intent) | import / Approve / будущий Apply | публикует площадки, не строки Estate |
| Inventory | нет | Init и сверка | нет |

## Явно вне периметра

- код lk-api и экраны LK;
- Apply-Run после `repo_ready` (читает `Plan.status`, пишет `Estate.status=applied`);
- каталог провайдеров и секреты (0015.2);
- смысл осей размещения (0015.1 §9) — здесь только поля.

## Последствия

- 0015.1 §12 становится отсылкой сюда.
- Следующий ADR на apply не переопределяет эти четыре объекта.
