# ADR-0012: CI/CD-платформа коллекции — Execution Environment, Harbor, Gitea, Semaphore UI, OpenBao

- **Статус:** Принято (архитектурное решение; реализация не начата)
- **Дата:** 2026-08-21
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

Сейчас в коллекции нет единого способа запуска плейбуков — три разных, независимо
сложившихся конвенции: `tests/ansible.cfg` (`roles_path = ../roles:~/.ansible/roles`),
`demo/*/ansible/ansible.cfg` (свой `roles_path`, свой inventory на каждый стенд), и
molecule-плейбуки (`converge.yml`/`verify.yml` каждого сценария на своём наборе group_vars).
Это уже приводило к реальным граблям: запуск не из той директории ломает `roles_path`
(`role 'reverse_proxy_traefik' was not found`), `poetry run --directory` подменяет cwd и ansible
не находит `site.yml`, `driver: vagrant` требует ручного экспорта `ANSIBLE_LIBRARY` перед каждым
molecule-прогоном (см. CLAUDE.md, «Molecule-тесты»).

Одновременно ROADMAP Backlog фиксировал две отдельные нереализованные идеи, обе явно требующие
ADR перед реализацией:

- №50 — веб-панель запуска ansible/terraform (кандидат — Semaphore UI);
- №52 — легковесный self-hosted git с CI/CD (кандидаты — Gitea/Forgejo), пересекающийся с №50
  по ответственности за CI vs CD.

Этот ADR закрывает оба пункта не по отдельности, а одним связным решением: локальная разработка,
CI и веб-панель запуска должны использовать **один и тот же** артефакт выполнения, а не
разъезжаться по трём независимым рантаймам, как это уже происходит с `roles_path`/venv сегодня.

## Решения

### 1. Execution Environment — единственный источник правды о рантайме

**Решение:** собирать Execution Environment (`ansible-builder`) с зафиксированной версией
`ansible-core>=2.20,<2.21` (как в `pyproject.toml`) и всеми зависимостями-коллекциями
(`community.postgresql`, `community.general` и т.д.), Python 3.12. Образ публикуется в **Harbor**
(новый компонент — self-hosted OCI registry, см. §6).

**Обоснование:** единственный артефакт, который потребляют и CI (Gitea Actions, §4), и Semaphore
(§5), и — опционально — локальный wrapper (§2), устраняет разъезжание версий, уже создающее
трение (`roles_path`/`ANSIBLE_LIBRARY`, см. «Контекст»).

**Граница scope:** EE закрывает только применение плейбуков к реальным хостам. `molecule` в него
не входит — vagrant/libvirt-драйверу нужен доступ к KVM с хоста, контейнеризация здесь не даёт
выигрыша; molecule остаётся на локальном poetry venv, как сегодня.

### 2. Wrapper для локальной разработки — не блокирует остальное

Локальный Makefile/скрипт, снимающий cwd/`roles_path`/`ANSIBLE_LIBRARY`-грабли — самостоятельная,
второстепенная задача, ортогональная остальным решениям этого ADR. Может вызывать
`ansible-navigator run` против EE (полный паритет с CI/Semaphore) либо остаться на локальном venv.
Конкретная реализация не выбрана — не блокирует §1/§3–§6.

### 3. Секреты — OpenBao, не HashiCorp Vault

**Решение:** секреты (пароль `ansible-vault`, terraform-переменные) — во внешнем **OpenBao**, не
в оригинальном HashiCorp Vault.

**Обоснование:** эмпирически подтверждено в этой же сессии (работа над `freeipa`,
см. `extensions/molecule/freeipa/molecule.yml`) — `vagrantcloud.com`, `releases.hashicorp.com`,
`api.cloud.hashicorp.com` и **`apt.releases.hashicorp.com`** (тот самый репозиторий, откуда
ставится пакет `vault`) отдают 404 «Content not available in your region» — устойчивый геоблок,
подтверждённый на 5+ независимых проверках, не разовый сбой инфраструктуры. Официальная установка
Vault идёт через тот же apt-репозиторий и с высокой вероятностью упрётся в тот же блок. OpenBao
(форк Vault под Linux Foundation после смены лицензии HashiCorp на BSL) API-совместим и
распространяется независимо от `hashicorp.com`.

Секреты читаются программно из OpenBao — и job runner'ом Semaphore (§5), и, при необходимости,
CI-раннером (§4) — вместо встроенного хранилища секретов Semaphore. Тот же принцип, что уже
описан для `Ansible Vault на уровне inventory` (`docs/adr/0004-mysql-ha-replication-role.md` §9,
`docs/adr/0001-reverse-proxy-npm-role.md` §5), но с внешним хранилищем вместо
зашифрованного файла в репозитории.

### 4. CI — Gitea + Gitea Actions; раннер для molecule — вне k3s

**Решение:** self-hosted git — **Gitea** (закрывает открытый в №52 вопрос Gitea vs Forgejo).
Сам сервер Gitea может жить в k3s (персистентный платформенный кластер, §6) как обычный
stateless-ish веб-сервис. Раннер Gitea Actions, исполняющий `molecule test` (нужен `/dev/kvm`,
nested-виртуализация, доступ к libvirt), сознательно вынесен **за пределы k3s** — обычный
systemd-сервис на хосте с реальным доступом к KVM, регистрируется в Gitea по сети, а не
планируется как под k8s.

**Обоснование:** доступ пода к `/dev/kvm` требует privileged pod + hostPath + жёсткую
node affinity — привязывает конкретную ноду кластера намертво и не даёт выигрыша от эластичности
k3s, раз раннер и так обязан жить на одном конкретном хосте с KVM. Отдельная systemd-инфраструктура
проще и согласуется с уже действующим по всей коллекции требованием `driver: vagrant`/
`provider: libvirt` для molecule (CLAUDE.md).

Более лёгкие CI-задачи (ansible-lint, сборка документации) при необходимости могут использовать
k3s-раннеры — это решение их не требует.

### 5. Веб-панель — Semaphore UI, репозиторий тянет из Gitea, без SSO на старте

**Решение:** веб-панель — **Semaphore UI** (закрывает открытый в №50 вопрос выбора панели).
Git-интеграция — напрямую из self-hosted Gitea (§4), не монтирование локального чекаута.
Task templates исполняются через EE-образ из Harbor (§1) — тот же артефакт, что и CI, без
четвёртого расходящегося рантайма.

**Авторизация:** без SSO на старте — basic-auth/встроенные локальные пользователи Semaphore, тот
же паттерн fail-fast-на-дефолтном-пароле, что уже используется в коллекции
(`reverse_proxy_traefik` dashboard, `infra_panel`, `reverse_proxy_npm` admin UI). Интеграция с
№49 (единая авторизация) — явный **follow-up**, не блокирует эту реализацию: №49 сама не
проработана архитектурно (см. ROADMAP), завязывать на неё уже большую инициативу — лишняя
зависимость.

### 6. Размещение — новая персистентная платформенная инфраструктура, не demo-стенд

**Решение:** Harbor (§1), Gitea+раннер (§4), OpenBao (§3), Semaphore UI (§5) живут на новой
персистентной инфраструктуре, тем же паттерном, что уже принят для `_server`-ролей
(`monitoring_server`, `backup_server`) — **не** добавляются в `demo/full-platform`.

**Обоснование:** `demo/full-platform` существует, чтобы показать все продуктовые роли коллекции
разом на одноразовых VM (ADR-0006). Эта CI/CD-подсистема — мета-инфраструктура, обслуживающая сам
процесс разработки коллекции, концептуально не «ещё один компонент платформы», который стенд
демонстрирует.

**Не проработано:** заводить ли Harbor/Gitea/OpenBao/Semaphore как новые роли коллекции
(`harbor`, `gitea`, `openbao`, `semaphore_ui`) по тому же generic-паттерну, что `backup_server`/
`monitoring_server` — либо считать их операторской инфраструктурой вне scope коллекции. Первый
вариант согласуется с уже принятым в коллекции принципом «свою инфраструктуру реализуем ролями»,
но окончательно не выбран — это первый конкретный шаг реализации, не решение этого ADR.

## Не проработано (следующие шаги)

- Конкретные роли (`harbor`, `gitea`, `openbao`, `semaphore_ui`) — defaults/vars/meta-зависимости,
  что каждая реально устанавливает.
- Где физически проверяется эта платформенная инфраструктура — новый постоянный
  demo-подобный стенд (например, `demo/cicd-platform`, terraform+molecule по прецеденту
  остальных `demo/*`) или отдельная нетипизированная площадка вне scope коллекции.
- Конкретная реализация wrapper'а (§2) — не выбрана, не блокирует остальное.
- Нужно ли переиспользовать k3s-паттерн `monitoring_server_k3s` (`xanmanning.k3s` + Helmwave) для
  Gitea, или заводить отдельный, более лёгкий k3s-инстанс только под платформенные сервисы.
- Разделение workflow между Gitea Actions (CI: lint + molecule) и Semaphore (CD: применение к
  реальной инфраструктуре) зафиксировано в §4/§5 на уровне ответственности, но конкретные
  task templates/workflow-файлы не спроектированы.
- Если геоблок HashiCorp (§3) когда-нибудь снимут или появится независимое зеркало — стоит
  перепроверить, не станет ли обычный Vault снова практичным вариантом; сейчас OpenBao — не
  идеологический, а вынужденный выбор.
