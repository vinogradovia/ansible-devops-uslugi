# ADR-0004: Роли `mysql_replication` и `proxysql` (отказоустойчивость и разгрузка чтения MySQL)

- **Статус:** Принято
- **Дата:** 2026-07-07
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

ТЗ — `docs/Requirements Specification/mysql-ha.txt`. Кратко: сейчас база сайта (заказы, анкеты,
каталог) живёт на одном сервере (primary), сервер никак не управляется этой Ansible-коллекцией.
Нужно закрыть две задачи:

1. **Отказоустойчивость** — DR-реплика в другом ДЦ Selectel, ручное переключение за минуты,
   ежесуточные архивные копии на отдельном хранилище.
2. **Разгрузка чтения** — read-реплика в том же ДЦ, читающий трафик приложения уходит на неё.

Явно исключено (зафиксировано в ТЗ и не пересматривается этим ADR): мультимастер-кластер
(Galera/InnoDB Cluster) и автоматическое переключение между ДЦ.

В коллекции уже есть смежная инфраструктура, на которую эта работа опирается:

- `monitoring_agent` уже умеет разворачивать `mysqld_exporter` (systemd или docker,
  `defaults/main.yml:140-153`) — новую роль это дублировать не должно, только дополнять
  alert-правила.
- `roles/monitoring_server/templates/alert-rules/mysql/mysqld-exporter.yml` уже содержит
  `MysqlDown` и другие алерты, но не отставание/разрыв репликации и не статус бэкапа — это
  добавляется в рамках данной работы.
- `infra_dns` (bind9) декларативно управляет зонами и умеет TTL только на уровне зоны
  (`$TTL` в `templates/zone.j2`), не на уровне отдельной записи — это ограничение придётся снять
  точечно (см. §6).
- **Важно:** `ROADMAP.md`, P0 №1 — VMAlert/Alertmanager сейчас не работает ни в docker-режиме
  (сервис отсутствует в `compose-monitoring-server.yml.j2`), ни в k3s-режиме (`helmwave up` в
  `monitoring-server.k3s.yml` закомментирован). Решение по этому ADR: **работа над Alertmanager
  вне скоупа** — роли этого ADR добавляют alert-rules и метрики, но их фактическая доставка
  оператору не гарантируется, пока P0 №1 не закрыт отдельно. Это заносится в открытые вопросы
  (§13) как блокер приёмочного критерия ТЗ п.8, а не решается здесь.
- Собственных ролей для СУБД, ProxySQL или бэкапов в коллекции пока нет.

## Решения

### 1. Состав новых ролей

**Решение:** две новые роли, а не одна:

- **`mysql_replication`** — всё, что выполняется *на серверах MySQL* (primary, read-реплика,
  DR-реплика): установка/adopt MySQL, конфигурация репликации, `read_only`, физические бэкапы
  (xtrabackup) и их выгрузка в S3, ручной promote DR-реплики.
- **`proxysql`** — ProxySQL на отдельных выделенных хостах (см. §6), с собственным жизненным
  циклом, не привязанным к жизненному циклу серверов БД.

**Обоснование:** ProxySQL разворачивается на других хостах (отдельные VIP-хосты, по ответу
на уточняющий вопрос), не имеет доступа к данным MySQL и может меняться независимо (например,
добавление ещё одной read-реплики в hostgroup ProxySQL не требует трогать роль `mysql_replication`).
Это то же разделение по объекту ответственности, что уже используется в коллекции
(`monitoring_server`/`monitoring_agent`, `docker`/потребители).

**Отклонено:** сторонняя Galaxy-роль вида `geerlingguy.mysql` — не подходит под требование
«adopt существующего primary без переустановки» (см. §2), а собственная логика GTID/failover
всё равно нужна поверх любой такой роли. Единственный прецедент внешней роли в коллекции —
`xanmanning.k3s`, взятая ради экономии на k3s-специфике, которой здесь нет.

### 2. Установка vs adopt существующего MySQL

**Решение:** роль `mysql_replication` поддерживает два пути на основании автономного
обнаружения:

- **Adopt** — если на хосте уже обнаружен работающий MySQL (проверка через факт наличия
  `mysqld`/сервиса, например `ansible.builtin.service_facts` + `command: mysqld --version`),
  роль **не переустанавливает** сервер: только добавляет конфигурацию, необходимую для
  репликации (drop-in файл `/etc/mysql/mysql.conf.d/99-mysql-replication.cnf` — `server_id`,
  `gtid_mode=ON`, `enforce_gtid_consistency=ON`, `log_bin`, `binlog_format=ROW`), заводит
  репликационного пользователя и выполняет discovery версии (см. ниже). Рестарт службы после
  правки конфигурации — не автоматический (`notify`, но хендлер помечен так, чтобы требовать
  явного подтверждения/окна, см. §9 «Процесс» ТЗ) — рестарт сервиса на боевом primary без
  согласованного окна недопустим.
- **Fresh install** — если MySQL не обнаружен (ожидаемый случай для read-реплики и
  DR-реплики), роль ставит MySQL из официального apt-репозитория (`repo.mysql.com`),
  GPG через `signed-by`-keyring (тот же паттерн, что и `roles/docker/tasks/install-repo.yml` —
  **не** `apt_key`), с версией, зафиксированной точно как на primary.

**Discovery версии:** версия не хардкодится в `defaults/main.yml` — читается runtime через
`SELECT VERSION()`/`mysqld --version` на primary и пробрасывается на реплики через
`hostvars[groups['mysql_primary'][0]].mysql_replication_discovered_version`. Требование к
структуре плейбука: play на группе `mysql_primary` должен отработать (или как минимум собрать
факты) **до** play на `mysql_read_replica`/`mysql_dr_replica` в рамках одного запуска —
зафиксировать это в README роли как обязательный порядок плеев.

**Поддержка ОС:** Debian/Ubuntu (apt) — совпадает с scope всей коллекции (см. ADR-0002 §4),
RHEL вне скоупа.

### 3. Инвентарная модель и параметр роли хоста

**Решение:** три группы инвентаря:

- `mysql_primary` (ровно один хост)
- `mysql_read_replica` (в том же ДЦ, что и primary)
- `mysql_dr_replica` (другой ДЦ Selectel)

Группы read/DR — во множественном числе намеренно (в отличие от `mysql_primary`): ProxySQL
уже поддерживает несколько backend-хостов в hostgroup (§6), так что на будущее (несколько
read-реплик) расширение не потребует переименования групп.

Переменная `mysql_replication_role: primary | read_replica | dr_replica` определяет ветвление
внутри роли (какие задачи выполнять — `CHANGE REPLICATION SOURCE`, `read_only`, источник
бэкапа и т.д.), задаётся через `group_vars` на уровне соответствующей группы, а не через
inventory hostvars поштучно.

### 4. Репликация

**Решение:** GTID (`gtid_mode=ON`, `enforce_gtid_consistency=ON`), формат бинлога `ROW` —
дословно по ТЗ. Реплицируется вся инстанция целиком, без `REPLICATE_DO_DB`/фильтров по схемам
(ответ на уточняющий вопрос — бэкапится и реплицируется всё).

Репликационный пользователь — отдельный, с минимальными правами (`REPLICATION SLAVE`,
`REPLICATION CLIENT`), пароль — обязательная переменная без дефолта в `defaults/main.yml`
(fail-fast через `assert`, по образцу `reverse_proxy_npm_admin_password` в ADR-0001 §5), значение
приходит из Ansible Vault на уровне inventory (см. §8).

Обе реплики: `read_only=ON`, `super_read_only=ON` — постоянно в обычном режиме, снимается только
задачей promote (§7).

**Топология репликации — «звезда», не цепочка:** обе реплики подключаются к primary напрямую
(`SOURCE_HOST` = адрес primary), а не read-реплика → DR как relay. Соответствует буквальной
формулировке ТЗ («обе реплики получают данные с основного»).

### 5. Шифрование трафика репликации между ДЦ

**Решение:** роль **не поднимает VPN** и не настраивает MySQL-native SSL для репликации.
МежДЦ-трафик репликации идёт через уже существующий WireGuard/IPsec-туннель (подтверждено:
связность между ДЦ уже есть) — `SOURCE_HOST` DR-реплики указывает на IP-адрес primary внутри
этой существующей приватной сети, а не на публичный адрес.

**Последствие:** роль полагается на внешнее условие (приватная сеть уже поднята и содержит
нужные хосты) — не проверяется автоматически (нет смысла добавлять `assert` на «адрес приватный»,
это было бы избыточной защитой от сценария, который эксплуатационно уже закрыт). Задокументировать
в README роли как явное предположение (bare inventory-переменная `mysql_replication_primary_host`
должна указывать приватный/туннельный адрес, не публичный IP).

### 6. Единая точка подключения: DNS → ProxySQL

**Решение:** вариант (a) из уточняющих вопросов — DNS-записи указывают на ProxySQL, ProxySQL
внутри решает маршрутизацию, а не DNS напрямую на MySQL-хосты:

- `db-write.<zone>` → адрес(а) ProxySQL — приложения пишут туда;
- `db-read.<zone>` → адрес(а) ProxySQL (тот же хост/кластер ProxySQL, отдельный порт или тот же —
  решение по listener'ам ProxySQL, не по DNS) — приложения читают оттуда.

ProxySQL hostgroups:
- writer-hostgroup (10): primary. Query rule — всё, что не строгий `SELECT`, туда.
- reader-hostgroup (20): read-реплика **only**. `SELECT`-трафик — туда через
  `mysql-query_rules` (`match_pattern: '^SELECT'`, `destination_hostgroup: 20`).
- DR-реплика **не входит** ни в один hostgroup ProxySQL в обычном режиме — ТЗ прямо запрещает
  грузить её боевым чтением. Появляется в writer-hostgroup только вручную в момент promote
  (см. §7).

**ProxySQL — отдельные выделенные хосты**, установка нативным пакетом из официального
apt-репозитория ProxySQL (`repo.proxysql.com`, тот же `signed-by`-паттерн), не через docker —
не создаём лишнюю зависимость от роли `docker` ради критичного компонента маршрутизации.

**Действие в `infra_dns`:** текущий `templates/zone.j2` поддерживает `$TTL` только на уровне
зоны целиком (`infra_dns_zone_default_ttl`/`zone.ttl`), а `db-write`/`db-read` нужны с коротким
TTL, не трогая TTL остальных записей зоны. Решение — точечное расширение шаблона: опциональный
`record.ttl` перед `IN` в строке записи (`{{ record.ttl ~ ' ' if record.ttl is defined else '' }}`),
обратно совместимое (без `record.ttl` поведение не меняется). Это небольшое расширение роли
`infra_dns`, а не новая роль.

### 7. Ручное переключение (promote)

**Решение:** переключение — управляемая, но **ручная** операция. Механизм — задачи роли
`mysql_replication`, спрятанные за тегами `mysql_replication_promote` + `never` (тот же паттерн,
что уже используется для `xanmanning.k3s` — тег `init`/`never` — и для
`monitoring_server_victoria_metrics_exporter_alerts`), т.е. никогда не выполняются в обычном
прогоне плейбука, только при явном `--tags mysql_replication_promote`.

Задача promote (запускается оператором вручную на хосте DR-реплики по написанной инструкции):
`STOP REPLICA` → `RESET REPLICA ALL` → `SET GLOBAL read_only=OFF, super_read_only=OFF`.
Обратное переключение (failback) и подключение ProxySQL к новому writer-хосту — отдельные шаги
той же written-инструкции, не автоматизируются полностью (ТЗ явно требует «ручное, по
инструкции», а не одну кнопку).

**Реализовано:** письменная пошаговая инструкция на русском (переключение, обратное
переключение, восстановление из копии) — отдельный документ,
[`docs/runbooks/mysql-failover.md`](../runbooks/mysql-failover.md), не часть роли, содержит
точные `ansible-playbook ... --tags ... --limit ...` команды, которые дергают эти task-файлы, а
также ручные SQL-команды для шагов, которые роль намеренно не автоматизирует (failback на
исходный primary, §7 сам документ).

### 8. Бэкапы

**Решение:** физический бэкап через `xtrabackup`/`mariabackup` (по версии MySQL), устанавливается
из официального Percona apt-репозитория (`repo.percona.com`, тот же `signed-by`-паттерн).

**Источник бэкапа по умолчанию — DR-реплика** (`mysql_replication_backup_source_role: dr_replica`,
переопределяемо): она и так не обслуживает боевое чтение, снятие бэкапа с неё не создаёт
дополнительной нагрузки ни на primary, ни на read-реплику. Оператор может переопределить на
`primary`, если по факту доступ к DR-реплике не подходит (например, на время, пока DR ещё не
до конца синхронизирована).

**Доставка в S3:** через `rclone` (статический бинарник, скачивается с проверкой checksum —
тот же паттерн, что уже используется для бинарников экспортеров в `monitoring_agent`, см.
`monitoring_agent_mysqld_exporter_binary_download_url`/`_checksum`), а не через `amazon.aws`
collection + boto3 — не добавляем новую Python-зависимость на управляемых хостах и новую
зависимость коллекции в `galaxy.yml` ради одной операции upload. `rclone` конфигурируется на
S3-совместимый эндпоинт Selectel object storage через переменные роли (endpoint, bucket,
access/secret key — из Vault, см. §9).

**Ретеншн — настраиваемый через переменные, три уровня:**
- ежедневные: `mysql_replication_backup_retention_daily: 14`
- еженедельные: `mysql_replication_backup_retention_weekly: 4`
- ежемесячные: `mysql_replication_backup_retention_monthly: 6`

Реализация — префиксы объектов в S3 по классу (`daily/`, `weekly/`, `monthly/`) с датой в имени,
отдельная задача удаляет объекты старше `retention_N * period` для каждого префикса. Шифрование
бэкапов at rest — не требуется (явный ответ на уточняющий вопрос).

**Алерт «бэкап не создался»:** задача бэкапа по завершении (success/failure через `rc`/
`failed_when`) пишет метрику через textfile-коллектор node_exporter (файл вида
`/var/lib/node_exporter/textfile_collector/mysql_backup.prom`, метрика
`mysql_backup_last_success_timestamp_seconds`) — требует, чтобы на хосте-источнике бэкапа
`monitoring_agent` уже включал node_exporter с `--collector.textfile.directory`, указывающим на
этот же путь (композиция на уровне инвентаря/плейбука, не meta-зависимость: роль
`mysql_replication` не должна тянуть за собой `monitoring_agent` — эти роли применяются к одному
хосту раздельно через плейбук оператора, как уже происходит для остальных ролей коллекции).
Alert-правило (`increase(time() - mysql_backup_last_success_timestamp_seconds > 90000)`
и т.п.) добавляется в `roles/monitoring_server/templates/alert-rules/mysql/`, рядом с
существующим `mysqld-exporter.yml`.

**Отставание/разрыв репликации:** используется уже существующий `mysqld_exporter` (он же
экспортирует `mysql_slave_status_*`, если включён флаг `--collect.slave_status` — проверить
и включить в `monitoring_agent_mysqld_exporter` при реализации). Порог алерта на отставание —
**300 секунд** (явный ответ на уточняющий вопрос). Оба алерта (lag > 300s, `Slave_IO_Running`/
`Slave_SQL_Running != Yes`) добавляются в тот же alert-rules файл.

### 9. Секреты

**Решение:** пароли (репликационный пользователь, admin ProxySQL, S3 access/secret key для
rclone) — переменные без дефолтов в `defaults/main.yml`, значения — в Ansible Vault на уровне
inventory (`group_vars/<group>/vault.yml`), тот же fail-fast `assert`-паттерн, что уже
использован в `reverse_proxy_npm` (ADR-0001 §5). Ansible Vault пока не используется в
коллекции нигде — это первый прецедент, задокументировать в README роли команду
`ansible-vault encrypt group_vars/mysql_primary/vault.yml` и как её передавать
(`--vault-password-file`/`--ask-vault-pass`), в соответствии с требованием ТЗ «пароли не
открытым текстом в переписке».

### 10. Molecule-тестирование — vagrant/libvirt

**Решение:** новый сценарий `extensions/molecule/mysql_replication/` с `driver` через
`molecule-plugins[vagrant]` и провайдером **libvirt** (уже есть на хосте разработчика — явный
ответ на уточняющий вопрос) — впоследствии, 2026-07-31, это стало единым обязательным требованием
для всех molecule-сценариев коллекции (см. CLAUDE.md, «Molecule-тесты»), но на момент этого ADR
было отличием от паттерна `nginx_multidomain`/`reverse_proxy_npm` (тогда ещё `driver: docker`).
Причина: репликации между несколькими полноценными MySQL-инстансами с systemd, сетевыми
интерфейсами и устойчивым состоянием диска удобнее проверять на полноценных ВМ, чем в контейнерах —
аналогичное обоснование уже использовано в ADR-0002 §8 для отказа от Docker-in-Docker.
Сценарий поднимает минимум три ВМ (primary/read_replica/dr_replica) через `Vagrantfile`,
converge прогоняет обе ветки (primary/adopt и replica/fresh install), verify проверяет реальный
`SHOW REPLICA STATUS` на обеих репликах.

**Зависимости для реализации:** добавить в `pyproject.toml`
(`dev`-группа) `molecule-plugins[vagrant] (>=25.8.0,<26.0.0)`; на хосте разработчика/CI — Vagrant,
`vagrant-libvirt` плагин, `qemu-kvm`/`libvirt` и box, совместимый с libvirt-провайдером
(например `generic/debian12` с Vagrant Cloud, а не `geerlingguy/docker-debian12-ansible`,
который собран только под docker-провайдер). Пошаговая инструкция по настройке этого окружения
(установка Vagrant, `vagrant-libvirt`, проверка `virsh list`) — обязательная часть реализации,
разместить в `roles/mysql_replication/README.md` (раздел «Локальное тестирование»), по аналогии
с тем, как остальные roles документируют молекулу в собственных README.

### 11. Взаимодействие с существующими ролями — только композиция, не meta-зависимости

**Решение:** ни `mysql_replication`, ни `proxysql` не объявляют `dependencies` на
`monitoring_agent`/`infra_dns` в `meta/main.yml`. Хосты MySQL/ProxySQL получают
`monitoring_agent` (для `mysqld_exporter`/`node_exporter`) тем же способом, что и остальные
управляемые хосты коллекции — через плейбук оператора, применяющий обе роли к одной группе
хостов. Это отличается от паттерна `docker` (безусловная/условная meta-зависимость), потому что
`docker` — обязательный инфраструктурный примитив без которого роль-потребитель не работает
вообще, а `monitoring_agent`/`infra_dns` — независимо конфигурируемые аспекты одного хоста,
которые логически не обязаны идти в комплекте (хост можно захотеть без мониторинга на время
отладки, например).

## Открытые вопросы / вне скоупа

- **Alertmanager (ROADMAP P0 №1) не работает** — без него алерты этого ADR технически не
  дойдут до оператора. Приёмочный критерий ТЗ п.8 не будет по-настоящему демонстрируем, пока
  этот P0-баг не закрыт отдельной работой. Зафиксировать зависимость в ROADMAP явной ссылкой на
  этот ADR.
- Автоматический failover — исключён ТЗ, не рассматривался и не будет рассматриваться в рамках
  этой архитектуры.
- Несколько read-реплик одновременно (сейчас — ровно одна) — инвентарная модель (§3) и
  hostgroup ProxySQL (§6) уже это позволяют, но балансировка между несколькими read-репликами
  (round-robin vs weighted) не проектировалась, т.к. не запрошена.
- RHEL/Rocky — вне scope, как и во всей коллекции (см. ADR-0002 §4).
- Поднятие самого WireGuard/IPsec-туннеля между ДЦ — вне scope этой роли (см. §5), связность
  считается предоставленной внешне.
- Шифрование бэкапов at rest в S3 — явно не требуется (см. §8), пересмотреть, если требования
  по комплаенсу изменятся.
