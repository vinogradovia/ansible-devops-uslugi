# ADR-0014: Платформенный контроллер — Module CRD, GitOps-синхронизация, Ansible как ядро изменений

- **Статус:** Принято (Фазы 0–6 реализованы и проверены реальным прогоном на живом стенде
  `platform/cicd`, см. `ROADMAP.md`, «Предлагаемая последовательность работ», пункт 7, и
  `platform-controller/README.md`; расширение охвата на остальные роли коллекции — открытая
  задача, см. «Не проработано» ниже)
- **Дата:** 2026-08-22
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

## Контекст

До сих пор `devops.uslugi` позиционировалась как набор переиспользуемых Ansible-ролей для
типовой DevOps-инфраструктуры клиентского хостинга (`docs/overview.md`) — каждая роль
разворачивается вручную (`ansible-playbook`) или, в перспективе, через веб-панель Semaphore
(`docs/adr/0012-cicd-platform-architecture.md` §5). Это по-прежнему верно на уровне механики
применения одного изменения, но не описывает более широкую цель: **платформу для управления
произвольной IT-инфраструктурой**, где Ansible-роли коллекции — не конечный продукт, а
исполнительное ядро под управлением декларативного, самонаблюдающего слоя.

Этот ADR фиксирует архитектуру этого слоя: K3s-кластер (одна нода или несколько) как рантайм
платформенного контроллера, `Module` — базовая единица управления (обёртка над существующей
Ansible-ролью), подсистема — функциональная группировка модулей (совпадает с уже принятыми в
`docs/overview.md` категориями: Мониторинг, Reverse proxy, DNS, HA БД, Backup, Identity/auth,
Периметр, Витрина). Расширяемость — главная цель модульности: новый тип управляемого
инфраструктурного сервиса добавляется новым модулем, не правкой ядра платформы.

## Решения

### 1. `Module` — CRD, обёртывающий существующую Ansible-роль

**Решение:** `Module` — Kubernetes custom resource. `spec` модуля — эквивалент `group_vars` для
конкретной роли коллекции (какая роль, какие переменные). Reconcile модуля не выполняет Ansible
напрямую — он инициирует job в Semaphore (§2), передавая туда `spec` как переменные запуска.

**Обоснование:** модуль не переизобретает то, что уже есть в роли — он декларативно описывает
**намерение** («эта роль должна быть применена с такими-то переменными к такому-то инвентарю»,
§4), а исполнение остаётся полностью на стороне уже работающего Ansible-конвейера (роль + EE
из Harbor, ADR-0012 §1). Это прямое продолжение принципа «Ansible — ядро управления
инфраструктурой» из контекста: контроллер оркестрирует *когда* и *что* запускать, но не *как*
именно применяется конкретный сервис — эта логика уже целиком в роли и не дублируется.

### 2. Контроллер оркестрирует Semaphore, не заменяет его

**Решение:** платформенный контроллер сам решает, когда и с какими параметрами запускать
модуль, и делает это через Semaphore API (task templates, тот же исполняемый артефакт — EE из
Harbor, ADR-0012 §5), а не через прямой вызов `ansible-runner`/`ansible-playbook` из своего
процесса. Semaphore остаётся: (а) ручным/аварийным путём для оператора в обход контроллера,
(б) единой системой просмотра — и автоматических запусков контроллера, и ручных — в одной
истории job'ов.

**Обоснование:** не плодить второй, отдельный от Semaphore, механизм исполнения и аудита
запусков — контроллер становится дополнительным *инициатором* существующего пайплайна
исполнения (ADR-0012), а не параллельной системой запуска Ansible со своим собственным логом.

### 3. Reconcile — непрерывное отслеживание дрейфа (GitOps), не разовое применение

**Решение:** контроллер не просто реагирует на создание/изменение `Module` CR разовым запуском —
он периодически переприменяет модуль (requeue-loop), даже если `spec` не менялся, обнаруживая и
устраняя дрейф состояния реальной инфраструктуры от декларации.

**Обоснование:** это прямо опирается на уже существующее и проверяемое молекулой свойство ролей
коллекции — идемпотентность (каждый molecule-сценарий обязан проходить фазу `idempotence` с
`changed=0`, см. `CLAUDE.md`). Периодическое переприменение безопасно и дёшево именно потому,
что идемпотентность ролей уже является жёстким требованием коллекции, а не допущением,
принимаемым специально для этого ADR. Побочный эффект: ручной Semaphore-прогон оператором (§2,
аварийный путь) не создаёт долгоживущего рассинхрона с декларацией — следующий цикл
reconcile контроллера просто подтвердит совпадающее состояние или переприменит модуль снова.

### 4. Git → K8s синхронизация — существующий инструмент (Flux/ArgoCD), не часть контроллера

**Решение:** синхронизацию `Module`-манифестов из git (self-hosted Gitea, ADR-0012 §4) в
Kubernetes берёт на себя готовый GitOps-инструмент (Flux или ArgoCD — выбор конкретного не
сделан, см. «Не проработано»). Платформенный контроллер — отдельный, более тонкий компонент,
реагирующий на `Module` CR, уже присутствующие в кластере, независимо от того, как именно они
туда попали (через GitOps-синхронизацию или `kubectl apply` вручную).

**Обоснование:** git↔K8s синхронизация — хорошо решённая задача с зрелыми инструментами;
переизобретать её внутри платформенного контроллера означало бы дублировать код ради
единственной выгоды «один бинарник вместо двух», не окупающей риск и объём работы. Разделение
ответственности чище: Flux/ArgoCD сводят git↔K8s, платформенный контроллер сводит K8s↔реальная
инфраструктура (через Semaphore/Ansible, §2/§3) — два независимых цикла согласования, каждый
своим специализированным инструментом.

### 5. Адресация хостов — ссылка на существующий inventory-файл, без нового CRD

**Решение:** `Module.spec` указывает путь/URL на уже существующий Ansible-inventory (в том же
git-репозитории, тем же способом, что сегодня `tests/inventory.yml`/`demo/*/ansible/inventory.yml`)
— не заводится отдельный Kubernetes CRD (`Host`/`InventoryGroup`) для декларативного описания
хостов внутри кластера.

**Обоснование:** K8s не обязан знать топологию инфраструктуры за пределами кластера — Ansible
уже решает эту задачу через inventory, и решает её полно (группы, per-host/per-group vars,
динамические источники). Дублирование этой модели вторым, K8s-native представлением хостов
добавило бы синхронизационную проблему (какой источник правды — CRD или inventory-файл при
расхождении) без выигрыша: `Module` и так уже ссылается на git как источник правды (§4), а
inventory-файл — часть того же репозитория.

## Не проработано (следующие шаги)

Пункты ниже — исходный список на момент принятия ADR. Актуальный статус после Фаз 0–6 (реальные
прогоны, см. `ROADMAP.md` пункт 7 и `platform-controller/README.md`):

- ~~Flux vs ArgoCD — конкретный выбор GitOps-инструмента для §4 не сделан.~~ **Решено (Фаза 2):**
  Flux (`source-controller`+`kustomize-controller` через Helmwave) — CRD-first, без второго web
  UI, легче для одной ноды. См. `platform/cicd/flux/README.md`.
- ~~Формат `status` подресурса `Module`... — не спроектирован.~~ **Решено (Фаза 1/3):**
  `status.conditions[Ready]`, `lastAppliedRevision`, `lastSyncTime`, `semaphoreJobID` —
  применены и проверены на живом стенде.
- ~~Период requeue-цикла (§3)... — компромисс не сделан.~~ **Решено (Фаза 4):** `driftInterval`
  30с (пилотное значение) — `RequeueAfter` после terminal-статуса `Ready`, проверено реальным
  циклическим прогоном без дублей.
- ~~Соответствие «модуль ↔ роль» 1:1 или композиция... — не решено.~~ **Решено (Фаза 6):**
  `Module.spec.role` указывает на playbook, а не обязательно на одну директорию `roles/*` —
  плейбук может композировать несколько top-level ролей подряд обычным списком `roles:`, без
  нового механизма на уровне CRD. Подтверждено composition-тестом
  `reverse_proxy_traefik`+`infra_panel` (двойная идемпотентность через drift-check).

Реально остающиеся открытыми:

- Как контроллер физически вызывает Semaphore API — реализовано (`internal/semaphore/`,
  `Authorization: Bearer`), но соответствие `Module.spec.role` → конкретный Semaphore task
  template id по-прежнему не выражено декларативно — сейчас это ручное сопоставление при
  создании Task Template, не часть схемы `Module` CRD.
- Отношение к уже существующим `demo/*` стендам и molecule-сценариям — остаются ли они
  самостоятельным механизмом тестирования ролей в отрыве от Module/контроллера, или тоже
  переезжают на этот механизм — не решено, вероятно нет (demo/molecule — про проверку ролей
  до релиза, Module/контроллер — про эксплуатацию уже выпущенных ролей).
- Расширение охвата контроллера на остальные роли коллекции за пределами `infra_panel`/
  `reverse_proxy_traefik` (Фаза 6 в широком смысле) — не детализировано, включая то, как
  выражать HA-роли с ручным promote/failover (`mysql_replication`, `postgresql_replication`,
  `proxysql`, `odyssey`), плохо сочетающиеся с автоматическим drift-reconcile.
- Секреты для Task Template (admin-пароли целевых сервисов, SSH-ключи) читаются либо из
  Semaphore Environment/Key напрямую, либо (для самой платформы) из OpenBao — см.
  `docs/adr/0016-openbao-secrets-pki.md` — но `Module.spec.vars` для пилотных модулей
  (`infra-panel-pilot`) по-прежнему хранит пароли открытым текстом в git (`platform/gitops`),
  не в OpenBao — не проработано.
