# ADR-0011: Роль `freeipa` (standalone LDAP/Kerberos-каталог) и её место в единой авторизации

- **Статус:** Роль реализована (standalone-сервер, без репликации и без управления данными
  каталога); федерация OAuth/OIDC поверх неё — открытая идея, не реализовано.
- **Дата:** 2026-08-20
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление)

## Контекст

Сервисы коллекции (`reverse_proxy_traefik` dashboard, `infra_panel`, `reverse_proxy_npm` admin UI,
Grafana внутри `monitoring_server`, Bareos webui внутри `backup_server`) сейчас авторизуются
независимо друг от друга — там, где авторизация вообще есть, это basic-auth с htpasswd-хэшем,
который каждая роль генерирует и хранит сама (см. ROADMAP Backlog №49). Единого набора
пользователей/групп и тем более SSO между сервисами нет.

Роль `freeipa` — первый шаг к единому каталогу: standalone-сервер
[FreeIPA](https://www.freeipa.org/) (LDAP + Kerberos KDC + собственный CA), развёрнутый через
`ipa-server-install`. Она сознательно **не** заводит пользователей/группы и не покрывает
репликацию/клиентов — только провижининг самого сервера (см. `roles/freeipa/README.md`,
«Назначение и границы»).

## Решения

### 1. Целевая ОС — Rocky/AlmaLinux 9, а не Debian/Ubuntu

**Найдено эмпирически** (первый прогон molecule): пакета `freeipa-server` для Ubuntu/Debian не
существует — их репозитории публикуют только `freeipa-client`/`freeipa-common`. Единственная роль
коллекции на RHEL-семействе (`dnf`/AppStream), остальные — Debian/Ubuntu (`apt`). Молекул-сценарий
(`extensions/molecule/freeipa/`) и весь провижининг рассчитаны на это.

### 2. Без встроенного DNS FreeIPA

`ipa-server-install` запускается без `--setup-dns` — отдельный DNS-сервер ради одной роли платформы
не поднимается. Резолвинг обеспечивается либо `freeipa_manage_hosts_entry: true` (дефолт,
self-entry в `/etc/hosts`), либо внешним `infra_dns` этой коллекции — тот же принцип «один источник
истины», что и в других ролях коллекции.

### 3. Роль — только каталог, не оркестратор авторизации

`freeipa` разворачивает LDAP/Kerberos-хранилище, но не решает, как остальные роли коллекции его
используют. Это сознательная граница (см. `docs/adr/0008-infra-panel-role.md` §3, тот же принцип
«роли коллекции не имеют архитектурной связности друг с другом сверх явно решённого») — иначе роль
пришлось бы тянуть зависимостями во все потребляющие роли сразу, не имея ещё ни одного реального
потребителя.

## Идея (не реализовано): OAuth/OIDC как приоритетный слой поверх `freeipa`

Зафиксирована как идея, а не решение — требует отдельного ADR перед реализацией. Соответствует
ROADMAP Backlog №49.

- **Приоритет — OAuth2/OIDC**, не прямой LDAP/Kerberos-бind в каждой роли-потребителе: современный
  протокол, нативная поддержка есть у большинства сервисов стека (Grafana, Traefik
  `forwardAuth`-middleware, NPM), не требует SSSD/`ipa-client-install` на каждом хосте-потребителе.
  `freeipa` в этой схеме — источник учётных записей, а не сам identity provider для OIDC: нужен
  федерационный слой поверх LDAP (в README `freeipa` уже упомянут как ожидаемый, но нереализованный
  сосед — Keycloak, «отдельная роль, ещё не реализована»).
- **LDAP/Kerberos напрямую — fallback**, для сервисов, которые OIDC не умеют и остаются на
  basic-auth-only админках (`reverse_proxy_traefik`/`infra_panel` dashboard) — там `freeipa` был бы
  источником пароля/хэша либо через `ipa-client-install` + SSSD на хосте, либо через прямой LDAP-bind
  в самой роли (ни то, ни другое не реализовано).

Открытые архитектурные вопросы (сознательно не решены сейчас):

1. Нужна ли отдельная роль `keycloak`/`oauth_provider` (federation-слой поверх `freeipa` по образцу
   `_server`/`_agent`) — README `freeipa` уже называет её ожидаемым соседом, но она не заведена.
2. Как роли-потребители переключаются между basic-auth/LDAP/OAuth — общая переменная вида
   `*_auth_method` (по образцу `*_backup_tool`, ADR-0010) или отдельная интеграционная роль поверх
   каждой из них.
3. Подключение `freeipa` как зависимости — `meta`-зависимость (как `docker`, ADR-0002 §2) или
   композиция на уровне плейбука (как `monitoring_agent`/`infra_dns`, ADR-0004 §11)? Пока не решено,
   поскольку нет ни одного реального потребителя.
