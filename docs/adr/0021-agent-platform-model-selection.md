# ADR-0021: Модель и движок локального инференса платформы — llama.cpp + Qwen3.6-35B-A3B, эмбеддинги bge-m3 (пилот)

- **Статус:** Реализовано и живо проверено (2026-09-06) на `platform/aicd-devops-labs-ru`, нода
  `llm1` — RAM увеличена до 25600 МиБ (25 ГиБ, §3), llama-server (`Qwen3.6-35B-A3B-UD-Q4_K_M`) и
  TEI (`BAAI/bge-m3`) развёрнуты в namespace `llm`, chat completion / tool-calling / эмбеддинги
  проверены реальными HTTP-запросами. Подробности — §«Реализация» в конце документа.
- **Дата:** 2026-09-05
- **Авторы:** Ivan Vinogradov (решения), Claude Code (оформление по итогам обсуждения)

> Первая версия этого ADR (в тот же день) выбирала vLLM + `Qwen2.5-14B-Instruct-AWQ` на основе
> общих критериев (VRAM-бюджет, зрелость tool-calling парсера). В процессе обсуждения выяснилось,
> что на эту платформу мигрирует конкретный существующий проект с уже работающей, отличной от
> предположенной конфигурацией — решение пересмотрено с учётом этого факта, а не гипотетически.
> Причины разбора обеих версий оставлены в тексте (§1–§2), а не стёрты — они объясняют, почему
> выбор именно такой, а не наоборот.

## Контекст

ADR-0015 решил, *как* запускать инференс (изолированный `RuntimeClass: nvidia`, гейтвей LiteLLM
перед моделью), но не *чем именно* и не *какими моделями* — §6 того ADR называл vLLM/TEI как
рабочий пример, не решение (см. уточнение там же от 2026-09-05). Вводные, зафиксированные в
обсуждении (в репозитории нигде не были записаны до этого ADR):

| Параметр | Значение |
|---|---|
| GPU `llm1` | RTX 5060 Ti, **16 ГБ VRAM** |
| RAM `llm1` | **10 240 МиБ (10 ГБ)** — реальное значение, `platform/aicd-devops-labs-ru/terraform/variables.tf` (`llm1_memory`, из `GET .../config`) |
| Внешние API (OpenAI/Anthropic/…) | Не подключаются на момент первой версии этого ADR |
| Приоритет для локальной модели | Надёжный function/tool-calling для MCP-gateway важнее качества генерации кода и важнее низкого latency |

### Новый факт: реальный проект-мигрант — `moon-local-engineer`

`/opt/integrus_local/devops-labs.ru/moon-local-engineer/` — не абстрактный будущий потребитель, а
существующий продукт, который переезжает на эту платформу: локальный агент мониторинга
инфраструктуры (`collect → bots → Middle SRE/Dev (локальная LLM) → Senior SRE/Dev (платная LLM) →
whitelist execute → Notifier`). Это **не тот же контур, что пять агентов ADR-0015** — свой
оркестратор (systemd-таймер каждые 15 минут, не Temporal), свой Tool Plane (OpenAPI, MCP —
опциональный адаптер, не основной транспорт), своя Knowledge Plane (Markdown-карточки). Общее —
только одна точка: обоим нужен OpenAI-совместимый локальный LLM-эндпоинт.

Его `CLAUDE.md` документирует уже работающую (хотя и помеченную «эксперимент/trial», с откатом на
Ollama) конфигурацию:

- движок — **`llama.cpp` `llama-server`**, не vLLM;
- модель — **`Qwen3.6-35B-A3B`, GGUF, квант `Q4_K_M`** (~21 ГБ), sparse MoE — активно на токен
  лишь ~3 млрд параметров из 35 млрд, релиз апрель 2026;
- флаги под ту же карту 16 ГБ VRAM: `--n-gpu-layers 99 --n-cpu-moe 17 --flash-attn on`,
  KV-cache `q8_0`, `--reasoning off`, `--jinja`, порт `:11435`, OpenAI-совместимый API;
- независимая находка того же класса, что приоритет §Контекст: «Thinking выключен
  (`ENABLE_THINKING=false`), иначе ломается JSON-вывод» — reasoning-режим Qwen ломает строгий
  структурированный вывод не только в MCP tool-calls (гипотеза этого ADR), но и в
  Pydantic-JSON-схемах (уже подтверждённый факт другого проекта);
- отдельно документирован план аренды GPU под «локальную 32B» — сигнал, что даже в исходном
  проекте эта конфигурация не считается окончательной.

Решающая находка — не в CLAUDE.md, а в этом же репозитории: **10 ГБ RAM на `llm1` — вероятно,
недостаточно** для `--n-cpu-moe 17` на модели такого размера (см. §3). Флаги из `moon-local-engineer`
почти наверняка подбирались не под эту конкретную VM.

Решения пользователя, зафиксированные при разборе (2026-09-05):

1. **`llm1` — действительно целевой хост.** RAM необходимо увеличивать, а не искать другую ноду.
2. **Внешний Senior-ярус `moon-local-engineer`** (платный API, например xAI Grok) — открытый
   вопрос, не решается в рамках этого ADR (см. «Не проработано»).
3. **Движок инференса платформы пересматривается в пользу `llama.cpp`.**

## Решения

### 1. Движок — `llama.cpp` `llama-server`, не vLLM

**Решение:** локальный LLM-инференс платформы обслуживает `llama-server`, а не vLLM.

**Обоснование:** ключевой критерий — зрелость offload'а MoE-экспертов на CPU при недостатке VRAM,
а не общие бенчмарки пропускной способности. У `llama.cpp` это простой и давно обкатанный флаг
`--n-cpu-moe`: первые N слоёв MoE-экспертов держатся в системной RAM, attention остаётся на GPU.
У vLLM аналогичный механизм (GPU-кэш горячих экспертов + CPU pinned memory с LFRU-вытеснением)
существует, но как минимум один относящийся к нему сценарий (инкрементальный offload,
`vllm-project/vllm#38256`) на момент проверки — ещё открытый RFC, не смержено. Для платформы,
которой прямо сейчас (а не гипотетически) нужно разместить 35B MoE-модель на 16 ГБ карте, зрелый
путь важнее потенциально более элегантного, но незавершённого.

Решающий довод — не абстрактный, а эмпирический: **`moon-local-engineer` уже гоняет именно эту
связку на identичной модели GPU** (RTX 5060 Ti, тот же VRAM-бюджет). Это не мысленный
эксперимент, а работающий (пусть и промаркированный «trial» в исходном проекте) прецедент.
Абстракция гейтвея не страдает: у `llama-server` и vLLM одинаково OpenAI-совместимый HTTP API,
LiteLLM (ADR-0015 §6) одинаково фронтит любой из них — смена движка не меняет ничего для
агентов ADR-0015 или для `moon-local-engineer`, оба видят только `svc litellm`/псевдоним модели.

### 2. Модель — `Qwen3.6-35B-A3B`, GGUF `Q4_K_M`, не `Qwen2.5-14B-Instruct`

**Решение:** основная локальная модель — `Qwen3.6-35B-A3B` в кванте `Q4_K_M`.

**Обоснование:** первая версия этого ADR выбирала `Qwen2.5-14B-Instruct-AWQ` — на момент того
выбора не было известно о существовании более новых альтернатив за пределами среза знаний
(релиз Qwen3.6 — апрель 2026, почти на два года позже Qwen2.5). Sparse-MoE архитектура
(35B суммарно, ~3B активных на токен) даёт при офлоаде экспертов на CPU доступ к существенно
более способной модели на той же карте 16 ГБ, чем позволяет плотная модель, которая обязана
целиком помещаться в VRAM. Формат GGUF — прямое следствие выбора движка (§1), не отдельное
решение: `llama.cpp` нативен для GGUF, vLLM — нет.

**Оговорка, которую нельзя опускать:** сама эта конфигурация в `moon-local-engineer` помечена
«эксперимент/trial», с явным путём отката на Ollama, и там же зафиксирован план аренды GPU под
локальную 32B-модель — то есть даже её автор не считает выбор окончательным. Для пилота этой
платформы это тем не менее лучший эмпирически проверенный вариант из доступных: не гипотеза с
чистого листа, а конфигурация, для которой уже известно, что она в принципе запускается на этой
модели GPU. Специализация под конкретного агента (`ai coding agent` отдельной моделью и т.п.)
по-прежнему не рассматривается — см. «Явно вне периметра».

### 3. RAM `llm1` — блокирующая предпосылка, требуется увеличение

**Решение:** прежде чем разворачивать эту конфигурацию, `llm1_memory` (Terraform-переменная,
сейчас `10240` МиБ) увеличивается. Ориентировочная цель — **не менее 16 ГБ, с запасом до 24 ГБ**;
точное значение фиксируется по факту измерения (см. «Верификация»), не этим ADR.

**Обоснование — грубая, явно помеченная как оценка, прикидка бюджета:**

| Статья | Оценка |
|---|---|
| GGUF-файл целиком | ~21 ГБ |
| Помещается в 16 ГБ VRAM (веса + KV-cache + служебные буферы flash-attn) | ~13–14 ГБ |
| Остаток, уходящий в системную RAM через `--n-cpu-moe 17` | ~7–8 ГБ |
| Системный оверхед ноды (k3s-agent, containerd, `nvidia-device-plugin`, `dcgm-exporter`, `node-exporter` — нода с taint `dedicated=agents`, но не пустая) | ~1.5–2.5 ГБ |
| **Итого потребность** | **~9–10.5 ГБ** |

При таком счёте нынешние 10 ГБ — не «тесно», а **на грани или за гранью** ещё до реального
измерения. Это объясняет, почему конфигурация, работающая на исходном железе
`moon-local-engineer`, на `llm1` рискует падать по OOM или уходить в своп — не потому, что флаги
неверны, а потому что RAM-бюджет ноды рассчитан не под эту нагрузку. Отдельно, некритично для
самого запуска, но влияет на пропускную способность: декодирование офлоаженных на CPU экспертов
упирается в скорость чтения RAM теми же 4 vCPU `llm1` — это не блокирует запуск, но обозначено как
предмет отдельного измерения производительности, не входит в блокирующую предпосылку.

### 4. VRAM/RAM-флаги — унаследованные от `moon-local-engineer` как стартовая точка, не догма

**Решение:** флаги `llama-server` на `llm1` стартуют с тех же значений, что уже проверены на
идентичной модели GPU: `--n-gpu-layers 99 --n-cpu-moe 17 --flash-attn on`, KV-cache `q8_0`.
`--n-cpu-moe 17` подлежит повторной калибровке на реальном `llm1` (свободная VRAM после
служебных процессов может отличаться), не переносится бездумно как финальное значение.

**Обоснование:** переизобретать подбор этого параметра с нуля дороже и рискованнее, чем начать с
уже проверенного значения и подстроить по факту — тот же принцип, которым руководствовались при
выборе самой модели (§2). TEI остаётся на CPU (`RuntimeClass: runc`), не на GPU — решение из
первой версии этого ADR не пересматривается: аргумент был не про движок чат-модели, а про то, что
вся карта должна доставаться LLM-серверу, и он не изменился с приходом `llama.cpp`.

### 5. Tool-calling — `llama-server --jinja`, с явно непроверенным риском формата `arguments`

**Решение:** `llama-server` запускается с `--jinja` (рендеринг штатного chat-темплейта модели,
включая tool-use часть). Qwen — в списке моделей, официально документированных как рабочие с этим
флагом.

**Обоснование и явно непроверенный риск:** в отличие от `moon-local-engineer` (которому нужен
только надёжный JSON по Pydantic-схеме, не формат OpenAI `tool_calls`), пяти агентам ADR-0015
нужен именно `tool_calls` в формате, которым пользуется MCP-gateway. Здесь есть задокументированный
открытый баг апстрима (`ggml-org/llama.cpp#20198`): `llama-server` в некоторых случаях отдаёт
`arguments` внутри `tool_calls` как JSON-объект, а не как JSON-строку, которую требует спецификация
OpenAI — это ломает совместимость со строгими OpenAI SDK-клиентами. **Требует сверки до
продакшен-использования:** совместим ли конкретно используемый в MCP-gateway HTTP-клиент с этим
расхождением или ломается на нём. Если ломается — обходной путь (собственный парсер на стороне
MCP-gateway либо `--chat-template-file` с доработанным темплейтом) — задача реализации, не
архитектурное решение этого ADR.

### 6. Эмбеддинги — `BAAI/bge-m3`, без изменений

**Решение:** без изменений относительно первой версии этого ADR — TEI обслуживает
[`BAAI/bge-m3`](https://huggingface.co/BAAI/bge-m3) на CPU (`cpu-*` образ TEI).

**Обоснование:** выбор эмбеддинг-модели не зависел от движка чат-модели и не зависит от смены
vLLM→llama.cpp — мультиязычность (100+ языков, включая русский) остаётся решающим критерием для
корпуса этой коллекции и будущих клиентских KB. Пересмотра не требуется.

### 7. Веса — конкретный источник GGUF-квантования пинуется явно, не «любой на HuggingFace»

**Решение:** для GGUF-репозитория `Qwen3.6-35B-A3B` фиксируется один источник квантования (на
момент реализации — переносится решение о том, чей именно репак использовать:
`unsloth`/`bartowski`/`lmstudio-community`/`ggml-org`, у каждого — самостоятельно
опубликованный `Q4_K_M`) и конкретная ревизия/коммит, не ветка `main`. Скачивание — bootstrap-
задачей на `PersistentVolumeClaim` (нода `llm1`, единственная с GPU).

**Обоснование:** GGUF-экосистема — не один канонический репозиторий, как было с
`Qwen/Qwen2.5-14B-Instruct-AWQ` (первая версия этого ADR), а несколько независимых third-party
реквантований одной и той же модели, потенциально с разными калибровочными данными и незаметно
разным качеством. Прямое повторное применение находки ADR-0007 §10.2 (вред незакреплённых
`:latest`) — здесь риск выше, чем просто «апстрим обновит чекпоинт»: сам выбор *какого* репака
использовать — решение, которое нужно принять один раз и явно, а не подразумевать первым
попавшимся результатом поиска.

### 8. LiteLLM — псевдоним модели без изменений; резерв под внешний provider теперь не абстрактный

**Решение:** без изменений в механике — агенты обращаются к модели через псевдоним
(`local-default`), не по идентификатору весов. Резерв под внешний provider остаётся
незаполненным (пункт 2 решений пользователя, §Контекст) — но теперь это не гипотетическое
«когда-нибудь», а известная зависимость конкретного проекта-мигранта (`Senior`-ярус
`moon-local-engineer`). Само решение, встраивать ли `Senior`-вызовы `moon-local-engineer` в
платформенный LiteLLM или оставить их полностью снаружи (`SENIOR_BASE_URL` напрямую во внешний
API, в обход платформы), **сознательно не принимается этим ADR** — см. «Не проработано».

**Обоснование:** решение пользователя при разборе — явно отложить, не выбирать сейчас. Разница с
первой версией ADR не в самом решении (внешние провайдеры по-прежнему не подключены), а в его
статусе: раньше это был пункт «когда-нибудь в будущем», теперь — открытый вопрос с известным,
близким по времени поводом его закрыть.

## Явно вне периметра (v1)

- **Способ подключения `Senior`-яруса `moon-local-engineer`** — открытый вопрос, не пункт
  «когда-нибудь»; см. «Не проработано».
- **Точное финальное значение `--n-cpu-moe` и объёма RAM `llm1`** — §3 задаёт ориентир и
  обоснование, но не финальное число; калибровка — задача реализации.
- **Производительность CPU-офлоада на 4 vCPU `llm1`** — не блокирует запуск, но не измерена.
- **Специализация моделей по агенту** — единая модель на все потребители (платформенные агенты и
  `moon-local-engineer`), как и в первой версии ADR.
- **MIG / честное аппаратное разделение GPU** — вне охвата, решение ADR-0015 §8 в силе.
- **Fine-tuning/дообучение агентов на `dataset`** — отдельный пункт ADR-0015 «Не проработано».
- **Reranker** для `retriever`-сервиса (ADR-0015 §7) — не решается здесь.
- **Работоспособность `--n-cpu-moe`-конфигурации без GPU-passthrough простоя** — не проверялось,
  во что реально выливается совместное присутствие `dcgm-exporter`/`nvidia-device-plugin` и
  тяжёлого CPU-офлоада на одной ноде под нагрузкой.

## Не проработано (следующие шаги)

- **`Senior`-ярус `moon-local-engineer` после миграции** — идёт ли он через платформенный
  LiteLLM (тогда ADR-0021 §8 требует доработки: реальный provider, ключ в OpenBao, снятие
  пометки «зарезервировано, не подключено») или остаётся полностью вне платформы. Решение
  пользователя — явно отложено при разборе этого ADR, не забыто.
- **Совместимость формата `tool_calls.arguments`** у `llama-server` с реальным HTTP-клиентом
  MCP-gateway (§5) — не проверено, помечен как открытый баг апстрима.
- **Финальные `--n-cpu-moe`/объём RAM `llm1`** (§3) — ориентир дан, число — по факту измерения.
- **Какой именно репак GGUF использовать** (§7) — источник не выбран, только требование пинить
  ревизию у того, что будет выбрано.
- **Не решено, что происходит с самим `moon-local-engineer`, если его собственный план аренды GPU
  под 32B реализуется независимо** — платформенная модель (эта) и модель `moon-local-engineer`
  (после миграции) в этом случае могут снова разойтись; ревизия не планируется заранее.

## Верификация

1. `llama-server` с флагами §4 поднимается на `llm1` под `RuntimeClass: nvidia`; `nvidia-smi`
   внутри пода показывает потребление VRAM в границах §3, не расходящееся на порядок.
2. Реальное потребление RAM под нагрузкой (`free -h`/cgroup memory.current на хосте во время
   генерации) сверяется с оценкой §3 — если фактическое потребление вплотную подходит к пределу
   выделенной RAM, `llm1_memory` увеличивается дальше, а не оставляется «почти ОК».
3. Реальный tool-call через MCP-gateway — `agent-job` получает корректно распарсенный
   `tool_calls`, а не объект, который клиент MCP-gateway не смог разобрать (прямая проверка риска
   §5, не бумажная).
4. Сравнительный smoke-тест: тот же промпт на `moon-local-engineer` (`:11435`, если ещё доступен)
   и на новом платформенном инстансе дают структурно сопоставимый ответ — дешёвая перекрёстная
   проверка, что перенос конфигурации не потерял ничего важного по дороге.
5. `text-embeddings-inference:cpu-*` с `BAAI/bge-m3` — без изменений, проверка из первой версии

## Реализация (2026-09-06)

Разворачивание — задачи `platform/aicd-devops-labs-ru/ansible/site.yml` (namespace `llm`, каркас
которого завела Фаза 1 ADR-0015 §10), не Helm-релиз, тем же принципом, что RuntimeClass/
device-plugin в той же play. Веса скачиваются `initContainer`'ом прямо на `PersistentVolumeClaim`
(не отдельным k8s Job — проще, идемпотентность по конструкции: сверка размера файла с ожидаемым до
и после закачки). Конкретные пины (образы/GGUF-репак/ревизия) — `group_vars/platform_hosts.yml`,
не хардкод в самом плейбуке.

**Предусловие §3 закрыто.** `llm1_memory` увеличена пользователем вручную через Proxmox
(stop+start VM, холодный перезапуск — на лету hotplug для этой VM не настроен) с 10240 до 25600
МиБ (25 ГиБ — выбран верхний край ориентира §3 с запасом, а не 16 ГиБ). Terraform не может
применить это изменение сам (`memory` — под `lifecycle.ignore_changes` в `llm1-target.tf`,
осознанно, см. комментарий там же) — переменная в `variables.tf` обновлена только как фиксация
факта. Гостевой `free -m` показывает 25033 МиБ (не ровно 25600 — вероятно, часть зарезервирована
под GPU passthrough), `kubectl describe node llm1` — `Allocatable.memory` 25633888Ki.

**Найденные реальным прогоном проблемы (по хронологии, все исправлены):**

1. **TEI: `CrashLoopBackOff` без `startupProbe`.** `livenessProbe` начинает отсчёт сразу от старта
   контейнера — скачивание `BAAI/bge-m3` (~2.2 ГБ) при первом запуске занимает больше 90с
   (`periodSeconds: 30 × failureThreshold: 3`), под убивался по liveness раньше, чем успевал
   поднять порт 80, и уходил в CrashLoopBackOff, так и не становясь `Ready`. Исправлено —
   `startupProbe` с тем же путём `/health`, `periodSeconds: 10 × failureThreshold: 30` (300с),
   Kubernetes не запускает `readinessProbe`/`livenessProbe`, пока `startupProbe` не пройдёт.
2. **Идемпотентная проверка веса в `initContainer` читала весь файл целиком.** `wc -c < "$DEST"` —
   redirect в stdin лишает `wc` возможности `stat()`-нуть файл по имени, busybox `wc` в этом случае
   реально построчно читает все 20+ ГБ через pipe (~2 минуты чистого CPU при каждом идемпотентном
   старте пода, подтверждено `ps aux` — процесс `wc -c` с 98.9% CPU). Исправлено на `stat -c%s
   "$DEST"` (busybox `stat` поддерживает `-c`, как и GNU coreutils) — мгновенная проверка размера
   без чтения содержимого.
3. **`--reasoning off` — не существует в актуальной сборке `llama-server`.** Флаг, дословно взятый
   из `CLAUDE.md` `moon-local-engineer` (§4 этого ADR), устарел для образа
   `ghcr.io/ggml-org/llama.cpp:server-cuda12-b7739` (пин на момент первой реализации) — `error:
   invalid argument: --reasoning`, контейнер падал в CrashLoopBackOff сразу после старта, даже не
   доходя до загрузки модели. По `--help` актуальной сборки эквивалент — `--reasoning-budget N`
   (`0` — отключить thinking, тот же эффект, которого добивался исходный флаг; `-1` — не
   ограничивать). Исправлено на `--reasoning-budget 0`.
4. **`b7739` не знает архитектуру `qwen35moe` — нужна более новая сборка.** После исправления
   находки 3 модель начала грузиться, но падала на `error loading model architecture: unknown
   model architecture: 'qwen35moe'`. У Qwen3.6-35B-A3B архитектура — не чистый MoE, а гибрид
   MoE + Gated Delta Net (SSM-подобный механизм линейного внимания, видно по ключам метаданных
   `qwen35moe.ssm.*` в GGUF) — судя по всему, добавлена в llama.cpp позже, чем был выпущен `b7739`.
   Полный перебор доступных тегов `ghcr.io/ggml-org/llama.cpp` (пагинация API реестра — обычный
   первый запрос `tags/list` отдаёт не все теги, нужно проходить `Link: rel="next"` до конца)
   нашёл `server-cuda12-b9002` — заметно более новую сборку; на ней модель грузится, лог
   подтверждает `fused Gated Delta Net (autoregressive) enabled` / `(chunked) enabled`. Образ в
   `group_vars/platform_hosts.yml` обновлён на `b9002`.
5. **Пересоздание Deployment `llama-server` после серии живых `kubectl patch`/`kubectl set image`
   (сделанных для быстрой итерации на находках 1/3/4, не дожидаясь полного повторного прогона
   плейбука).** Первый после этого прогон `site.yml` показал `changed` для Deployment, даже когда
   применяемые значения совпадали с уже живыми (вероятно, из-за разных `fieldManager` у
   `kubectl patch`/`kubectl set image` и у модуля `kubernetes.core.k8s`) — разовая нормализация
   владения полями, не постоянная проблема: повторный (третий) прогон дал `changed=0` для всех
   задач `LLM:*`, идемпотентность подтверждена чисто.

**Проверено реальным прогоном (2026-09-06):** `nvidia-smi` внутри пода `llama-server` — 14492 из
16311 МиБ VRAM заняты (в границах оценки §3, ~13–14 ГБ); `free -h` на `llm1` под нагрузкой — 24 ГиБ
total, только 2.7 ГиБ used, 21 ГиБ available (RAM-предусловие §3 закрыто с явным запасом, не
«впритык»); `GET /health` обоих сервисов — `200`; `POST /v1/chat/completions` на llama-server —
корректный ответ без утечки `<think>`-содержимого (`--reasoning-budget 0` работает); тестовый
`tool_calls`-запрос — `arguments` возвращается корректной JSON-**строкой**
(`"arguments":"{\"city\":\"Москва\"}"`), а не объектом — риск §5 (`llama.cpp#20198`) на сборке
`b9002` не проявляется (не гарантия на будущее — баг апстрима остаётся открытым, проверено только
для конкретной использованной сборки и конкретных тестовых запросов); `POST /embed` на TEI —
реальный вектор эмбеддинга для русской фразы. Повторный прогон `site.yml` (третий по счёту) —
`changed=0` для всех задач `LLM:*`, под не пересоздавался, `restartCount: 0`.

**Не проверено (осталось на будущее, не блокирует текущий пилот):** верификация §3 (сравнение с
`moon-local-engineer`) — не выполнялась, требует доступа к тому проекту отдельным заходом;
verification §3 из списка выше (реальный tool-call через MCP-gateway) — MCP-gateway ещё не
развёрнут (ADR-0015, `ns: gateway` пока пустой каркас), проверен только прямой вызов
`/v1/chat/completions` с `tools`, не полный путь агент → gateway → модель; производительность
CPU-офлоада под длительной нагрузкой (throughput при заполнении контекста, не единичный короткий
запрос) отдельно не измерялась.
